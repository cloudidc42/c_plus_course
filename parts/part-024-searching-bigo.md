## 24.1 Linear Search: การค้นหาแบบพื้นฐานที่สุด (Step 185)

**Linear Search (การค้นหาเชิงเส้น)** คือวิธีค้นหาที่ตรงไปตรงที่สุด: ไล่ตรวจสอบสมาชิกในอาร์เรย์
ทีละตัวตั้งแต่ต้นจนจบ จนกว่าจะเจอค่าที่ต้องการ หรือไล่จนหมดอาร์เรย์แล้วไม่เจอ

ข้อดีที่สำคัญที่สุดของ Linear Search คือ **ใช้ได้กับข้อมูลทุกแบบ ไม่ว่าจะเรียงแล้วหรือไม่ก็ตาม**
เพราะมันไม่ได้อาศัยลำดับของข้อมูลเลย

### โค้ดสมบูรณ์

```c
/* ============================================================
 * ชื่อไฟล์:     linear_search.c
 * คำอธิบาย:     สาธิต Linear Search — ไล่ตรวจสอบทีละตัวจนกว่าจะเจอเป้าหมาย
 * ============================================================ */

/* ---------- 1. Header Includes ---------- */
#include <stdio.h>
#include <stddef.h>

/* ---------- 2. Macro / Constant Definitions ---------- */
#define ARRAY_SIZE 8

/* ---------- 3. Function Prototypes ---------- */
long linear_search(const int arr[], size_t n, int target);

/* ---------- 4. main() ---------- */
int main(void) {
    int data[ARRAY_SIZE] = {45, 12, 89, 3, 67, 23, 91, 8};

    int target = 67;
    long result = linear_search(data, ARRAY_SIZE, target);

    if (result != -1) {
        printf("พบค่า %d ที่ตำแหน่ง index %ld\n", target, result);
    } else {
        printf("ไม่พบค่า %d ในอาร์เรย์\n", target);
    }

    return 0;
}

/* ---------- 5. Function Implementations ---------- */
long linear_search(const int arr[], size_t n, int target) {
    for (size_t i = 0; i < n; i++) {
        if (arr[i] == target) {
            return (long)i;
        }
    }
    return -1; /* ไม่พบเป้าหมายเลย */
}
```

```bash
gcc -Wall -Wextra -Wpedantic -std=c17 linear_search.c -o linear_search
./linear_search
```

```
พบค่า 67 ที่ตำแหน่ง index 4
```

> **ทำไม `linear_search` คืนค่าเป็น `long` ไม่ใช่ `size_t`?** เพราะเราต้องใช้ `-1` แทนสถานะ
> "ไม่พบ" ซึ่ง `-1` เป็นค่าติดลบ ถ้าคืนเป็น `size_t` (unsigned) ค่า `-1` จะถูกตีความเป็นเลขบวก
> มหาศาลทันที (`SIZE_MAX`) ทำให้ตรวจสอบผิดพลาด — การเลือกชนิดข้อมูลคืนค่าที่ "รองรับค่าพิเศษ
> สำหรับกรณีไม่พบ" ได้ถูกต้องเป็นเรื่องสำคัญมากที่มือใหม่มักมองข้าม

### วิเคราะห์ความซับซ้อน

- **Best Case**: เป้าหมายอยู่ที่ตำแหน่งแรกสุด (`arr[0]`) → ตรวจสอบแค่ 1 ครั้ง → **O(1)**
- **Worst Case**: เป้าหมายอยู่ตำแหน่งสุดท้าย หรือไม่มีอยู่ในอาร์เรย์เลย → ต้องตรวจสอบครบทุกตัว
  → **O(n)**
- **Average Case**: โดยเฉลี่ยต้องตรวจสอบประมาณ n/2 ตัว (สมมติเป้าหมายมีโอกาสอยู่ตำแหน่งไหน
  ก็ได้เท่ากัน) → ยังคงเป็น **O(n)** เพราะค่าคงที่ (1/2) ถูกตัดทิ้งใน Big-O Notation (จะอธิบาย
  รายละเอียดในหัวข้อ 24.3)

Linear Search เหมาะกับข้อมูลขนาดเล็ก หรือข้อมูลที่ไม่ได้เรียงและไม่คุ้มค่าที่จะเรียงก่อน
(เช่นค้นหาแค่ครั้งเดียวในอาร์เรย์ที่สร้างขึ้นชั่วคราว) แต่ถ้าต้องค้นหาซ้ำๆ หลายครั้งในข้อมูล
ชุดเดิม การเรียงข้อมูลไว้ก่อนแล้วใช้ Binary Search มักจะคุ้มค่ากว่ามาก

## 24.2 Binary Search: การค้นหาแบบแบ่งครึ่ง (Step 186)

**Binary Search (การค้นหาแบบทวิภาค)** ใช้แนวคิดเดียวกับการเปิดพจนานุกรม: ถ้าเราหาคำที่ขึ้นต้น
ด้วย "ม" เราจะไม่เปิดจากหน้าแรกไล่ทีละหน้า แต่จะเปิดกลางเล่มก่อน แล้วดูว่าคำที่ต้องการอยู่
ก่อนหรือหลังหน้าที่เปิด แล้วตัดครึ่งที่ไม่เกี่ยวข้องทิ้งไปเลย ทำซ้ำแบบนี้ไปเรื่อยๆ

### ทำไม Binary Search ต้องการอาร์เรย์ที่เรียงแล้วเท่านั้น

หัวใจของ Binary Search คือการเปรียบเทียบค่าตรงกลาง (`arr[mid]`) กับเป้าหมาย แล้ว **ตัดสินใจ
ทิ้งข้อมูลครึ่งหนึ่งทันทีโดยไม่ต้องดูเลย**:

- ถ้า `target < arr[mid]` เราสรุปว่าเป้าหมาย **ต้องไม่อยู่** ในครึ่งขวา (`arr[mid..right]`)
  เลย แล้วค้นหาต่อเฉพาะครึ่งซ้าย
- ถ้า `target > arr[mid]` เราสรุปว่าเป้าหมาย **ต้องไม่อยู่** ในครึ่งซ้าย แล้วค้นหาต่อเฉพาะครึ่งขวา

การสรุปแบบนี้จะ **ถูกต้อง** ก็ต่อเมื่อข้อมูลเรียงลำดับอยู่แล้วเท่านั้น เพราะถ้าข้อมูลไม่เรียง
ค่าที่เราต้องการอาจซ่อนอยู่ฝั่งไหนก็ได้ ไม่ว่า `arr[mid]` จะมีค่าเท่าไหร่ — การตัดทิ้งครึ่งหนึ่ง
โดยไม่ตรวจสอบจะทำให้พลาดคำตอบที่ถูกต้องไปเลย

ตัวอย่างที่เห็นภาพชัด: อาร์เรย์ `[5, 1, 9, 3, 7]` (ไม่เรียง) หาค่า `3` ถ้าใช้ Binary Search
โดยดู `mid = arr[2] = 9` แล้วสรุปว่า `3 < 9` จึงค้นหาต่อเฉพาะครึ่งซ้าย `[5, 1]` — แต่ค่า `3`
จริงๆ อยู่ในครึ่งขวา (`arr[3] = 3`)! Binary Search จะรายงานผิดว่า "ไม่พบ" ทั้งที่ค่านั้นมีอยู่จริง

**นี่คือเหตุผลที่ Part 23 (Sorting) ต้องมาก่อน Part 24 (Searching) ในหลักสูตรนี้**: การเรียง
ข้อมูลให้ถูกต้องก่อนเป็นเงื่อนไขที่ Binary Search ต้องพึ่งพา

### โค้ดสมบูรณ์ (ทั้ง Iterative และ Recursive)

```c
/* ============================================================
 * ชื่อไฟล์:     binary_search.c
 * คำอธิบาย:     สาธิต Binary Search ทั้งแบบวนลูปและแบบเรียกซ้ำ
 * ============================================================ */
#include <stdio.h>
#include <stddef.h>

#define ARRAY_SIZE 10

long binary_search(const int arr[], size_t n, int target);
long binary_search_recursive(const int arr[], long low, long high, int target);

int main(void) {
    /* อาร์เรย์นี้ต้องเรียงแล้วเท่านั้น Binary Search ถึงจะทำงานถูกต้อง */
    int data[ARRAY_SIZE] = {2, 5, 8, 12, 16, 23, 38, 45, 56, 72};

    long result = binary_search(data, ARRAY_SIZE, 23);
    printf("[Iterative] หา 23 เจอที่ index %ld\n", result);

    long result2 = binary_search_recursive(data, 0, (long)ARRAY_SIZE - 1, 56);
    printf("[Recursive] หา 56 เจอที่ index %ld\n", result2);

    long not_found = binary_search(data, ARRAY_SIZE, 99);
    printf("หา 99 ได้ผลลัพธ์ index %ld (คาดว่าไม่พบ)\n", not_found);

    return 0;
}

long binary_search(const int arr[], size_t n, int target) {
    long low = 0;
    long high = (long)n - 1;

    while (low <= high) {
        long mid = low + (high - low) / 2; /* ป้องกัน overflow เทียบกับ (low+high)/2 */

        if (arr[mid] == target) {
            return mid;
        } else if (arr[mid] < target) {
            low = mid + 1;  /* ตัดครึ่งซ้ายทิ้ง รวมถึง mid เอง */
        } else {
            high = mid - 1; /* ตัดครึ่งขวาทิ้ง รวมถึง mid เอง */
        }
    }

    return -1; /* low > high แปลว่าค้นหาจนหมดขอบเขตแล้วไม่พบ */
}

long binary_search_recursive(const int arr[], long low, long high, int target) {
    if (low > high) {
        return -1; /* ฐาน: ขอบเขตค้นหาว่างเปล่าแล้ว ไม่พบเป้าหมาย */
    }

    long mid = low + (high - low) / 2;

    if (arr[mid] == target) {
        return mid;
    } else if (arr[mid] < target) {
        return binary_search_recursive(arr, mid + 1, high, target);
    } else {
        return binary_search_recursive(arr, low, mid - 1, target);
    }
}
```

```bash
gcc -Wall -Wextra -Wpedantic -std=c17 binary_search.c -o binary_search
./binary_search
```

```
[Iterative] หา 23 เจอที่ index 5
[Recursive] หา 56 เจอที่ index 8
หา 99 ได้ผลลัพธ์ index -1 (คาดว่าไม่พบ)
```

> **ทำไมใช้ `low + (high - low) / 2` แทน `(low + high) / 2`?** เพราะถ้า `low` และ `high`
> มีค่ามากพอ (ใกล้ค่าสูงสุดของชนิดข้อมูล) การบวก `low + high` อาจเกิด **Integer Overflow**
> ก่อนจะหารด้วย 2 ทำให้ได้ค่า `mid` ที่ผิดพลาด (Undefined Behavior สำหรับ signed integer)
> สูตร `low + (high - low) / 2` ให้ผลลัพธ์ทางคณิตศาสตร์เหมือนกันทุกประการ แต่ปลอดภัยกว่า
> เพราะ `high - low` มีค่าน้อยกว่าตัวแปรทั้งสองตัวเสมอ นี่คือ Best Practice ที่ใช้กันจริง
> ในไลบรารีระดับ Production

### Trace การทำงานของ Binary Search

ค้นหาค่า `23` ในอาร์เรย์ `[2, 5, 8, 12, 16, 23, 38, 45, 56, 72]` (index 0-9):

```
รอบที่ 1: low=0, high=9, mid=4 -> arr[4]=16
          16 < 23  -> ตัดครึ่งซ้ายทิ้ง (index 0-4)  -> low = 5

รอบที่ 2: low=5, high=9, mid=7 -> arr[7]=45
          45 > 23  -> ตัดครึ่งขวาทิ้ง (index 7-9)  -> high = 6

รอบที่ 3: low=5, high=6, mid=5 -> arr[5]=23
          23 == 23 -> พบเป้าหมาย! คืนค่า index 5
```

สังเกตว่าจากอาร์เรย์ 10 ตัว เราใช้เวลาแค่ **3 รอบ** ในการค้นหา เทียบกับ Linear Search ที่
อาจต้องตรวจสอบสูงสุดถึง 10 รอบ (หรือ 6 รอบถ้าไล่จากซ้ายไปเจอที่ index 5) — ยิ่งอาร์เรย์ใหญ่ขึ้น
ความต่างยิ่งเห็นชัด: อาร์เรย์ 1,000,000 ตัว Linear Search อาจต้องตรวจสอบถึง 1,000,000 ครั้ง
ในกรณีเลวร้ายที่สุด แต่ Binary Search ใช้แค่ประมาณ **log₂(1,000,000) ≈ 20 ครั้ง** เท่านั้น

### วิเคราะห์ความซับซ้อน

- **Best Case**: เป้าหมายอยู่ตรงกลางพอดีในรอบแรก → **O(1)**
- **Worst Case / Average Case**: ทุกรอบตัดขนาดปัญหาลงครึ่งหนึ่งเสมอ ทำให้จำนวนรอบสูงสุด
  คือ log₂(n) → **O(log n)**

## 24.3 Big-O Notation คืออะไรกันแน่ (Step 187)

เราพูดถึงคำว่า O(n), O(n²), O(log n) มาหลาย Part แล้วโดยยังไม่ได้อธิบายอย่างเป็นทางการ
ถึงเวลาทำความเข้าใจให้ชัดเจน

### นิยามอย่างง่าย

**Big-O Notation** คือสัญกรณ์ทางคณิตศาสตร์ที่ใช้อธิบายว่า **เวลาในการทำงาน (Time)** หรือ
**หน่วยความจำที่ใช้ (Space)** ของอัลกอริทึม **เติบโตเร็วแค่ไหน** เมื่อขนาดของข้อมูลนำเข้า
(`n`) เพิ่มขึ้น — มันไม่ได้บอกเวลาที่แน่นอน (เป็นวินาที) แต่บอก **แนวโน้มการเติบโต** เมื่อ `n`
มีค่ามากขึ้นเรื่อยๆ (เรียกว่า Asymptotic Behavior)

พูดง่ายๆ: Big-O ตอบคำถามว่า **"ถ้าข้อมูลเพิ่มเป็น 2 เท่า เวลาทำงานจะเพิ่มเป็นเท่าไหร่"**

| Class | ถ้า n เพิ่มเป็น 2 เท่า เวลาทำงานจะเป็นอย่างไร |
|---|---|
| O(1) | เท่าเดิม |
| O(log n) | เพิ่มขึ้นแค่ 1 หน่วย (บวก) |
| O(n) | เพิ่มเป็น 2 เท่า |
| O(n log n) | เพิ่มมากกว่า 2 เท่าเล็กน้อย |
| O(n²) | เพิ่มเป็น 4 เท่า |
| O(2ⁿ) | เพิ่มเป็น "ยกกำลังสอง" ของเวลาเดิม (ระเบิดทันที) |

### ทำไมต้องตัดค่าคงที่และเทอมที่เล็กกว่าทิ้ง

สมมติโค้ดหนึ่งมีเวลาทำงานจริงๆ ตามสูตร `T(n) = 3n² + 5n + 100` เราจะบอกว่าอัลกอริทึมนี้คือ
**O(n²)** เพราะเมื่อ `n` มีค่ามากขึ้นเรื่อยๆ (`n → ∞`) เทอม `3n²` จะ **ครอบงำ (dominate)**
เทอมอื่นทั้งหมดจนแทบไม่มีนัยสำคัญ:

| n | 3n² | 5n | 100 | สัดส่วนของ 3n² ต่อ T(n) ทั้งหมด |
|---|---|---|---|---|
| 10 | 300 | 50 | 100 | 66.7% |
| 100 | 30,000 | 500 | 100 | 98.0% |
| 10,000 | 300,000,000 | 50,000 | 100 | 99.98% |
| 1,000,000 | 3 × 10¹² | 5,000,000 | 100 | ~100.00% |

นี่คือเหตุผลที่ Big-O Notation:

1. **ตัดค่าคงที่ (Coefficient) ทิ้ง**: `3n²` เขียนแค่ `n²` เพราะเราสนใจ "รูปร่างการเติบโต"
   ไม่ใช่ตัวเลขที่แน่นอน (ค่าคงที่ขึ้นกับความเร็ว CPU, คอมไพเลอร์ ฯลฯ ซึ่งไม่ใช่คุณสมบัติของ
   อัลกอริทึมเอง)
2. **เก็บเฉพาะเทอมที่โตเร็วที่สุด**: `3n² + 5n + 100` เขียนแค่ `O(n²)` เพราะเทอมเล็กกว่า
   (`5n`, `100`) มีผลน้อยลงเรื่อยๆ เมื่อ `n` โตขึ้น จนแทบไม่มีนัยสำคัญ

### Big-O vs Big-Theta vs Big-Omega

ในเชิงวิชาการ มีสัญกรณ์ 3 แบบที่ใช้อธิบายขอบเขตการเติบโตของฟังก์ชัน แต่ในบทสนทนาทั่วไปของ
วงการโปรแกรมเมอร์ มักใช้คำว่า "Big-O" แทนทั้ง 3 แบบอย่างหลวมๆ (ทั้งที่ความหมายทางคณิตศาสตร์
เข้มงวดจริงๆ ต่างกัน) ควรเข้าใจไว้ดังนี้:

| สัญกรณ์ | ความหมายที่แท้จริง | ใช้บอกอะไร |
|---|---|---|
| **Big-O: O(f(n))** | ขอบเขตบน (Upper Bound) — อัลกอริทึม "ช้าไม่เกิน" อัตรานี้ | มักใช้พูดถึง Worst Case |
| **Big-Omega: Ω(f(n))** | ขอบเขตล่าง (Lower Bound) — อัลกอริทึม "เร็วไม่เกิน" อัตรานี้ | มักใช้พูดถึง Best Case |
| **Big-Theta: Θ(f(n))** | ขอบเขตทั้งบนและล่างพร้อมกัน (Tight Bound) — อัลกอริทึมโตด้วยอัตรานี้แน่นอน | ใช้เมื่อ Best/Worst Case เท่ากัน |

ตัวอย่างเช่น Insertion Sort: Best Case คือ Ω(n), Worst Case คือ O(n²) — เราไม่สามารถพูดว่า
Insertion Sort คือ Θ(n²) ได้ เพราะ Best Case กับ Worst Case ไม่เท่ากัน แต่ในบทสนทนาทั่วไป
คนมักพูดว่า "Insertion Sort คือ O(n²)" โดยหมายถึง Worst Case เป็นหลัก ซึ่งในทางปฏิบัติก็เพียงพอ
สำหรับการสื่อสารส่วนใหญ่ — ตลอดหลักสูตรนี้เราจะใช้คำว่า Big-O ในความหมายกว้างแบบที่ใช้กันทั่วไป
นี้เช่นกัน แต่ระบุ Best/Average/Worst Case แยกให้ชัดเจนเสมอเมื่อสำคัญ

## 24.4 Class ความซับซ้อน: O(1) และ O(log n) (Step 188)

### O(1) — Constant Time

อัลกอริทึมที่ใช้เวลาทำงาน **คงที่เสมอ ไม่ว่าขนาดข้อมูลนำเข้าจะเป็นเท่าไหร่**

ตัวอย่างจากที่เรียนมาแล้วในหลักสูตรนี้:

- การเข้าถึงสมาชิกอาร์เรย์ผ่าน index โดยตรง `arr[5]` (Part 7) — ไม่ว่าอาร์เรย์จะมี 10 ตัว
  หรือ 10 ล้านตัว การเข้าถึง `arr[5]` ใช้เวลาเท่ากันเสมอ เพราะ CPU คำนวณตำแหน่งหน่วยความจำ
  ได้โดยตรงจากสูตร `base_address + index * sizeof(type)`
- การ push/pop สมาชิกที่ปลายของ Stack แบบ Array-based (Part 20)
- การเข้าถึงข้อมูลใน Hash Table ในกรณีเฉลี่ยที่ไม่มี Collision มาก (Part 22) — เรียกว่า
  **Amortized O(1)**

```c
int get_first_element(const int arr[], size_t n) {
    if (n == 0) {
        return 0;
    }
    return arr[0]; /* เข้าถึงโดยตรง ไม่ต้องวน loop เลย ไม่ว่า n จะเท่าไหร่ */
}
```

### O(log n) — Logarithmic Time

อัลกอริทึมที่ **ตัดขนาดปัญหาลงเป็นเศษส่วนคงที่ (มักเป็นครึ่งหนึ่ง) ในทุกขั้นตอน**

ตัวอย่างที่ชัดที่สุดคือ **Binary Search** จาก 24.2 — ทุกรอบตัดข้อมูลทิ้งครึ่งหนึ่งเสมอ ทำให้
จำนวนรอบสูงสุดคือ log₂(n) ตัวอย่างอื่นๆ:

- การค้นหา/แทรก/ลบใน Binary Search Tree ที่สมดุล (Part 21) — เดินลงต้นไม้ทีละระดับ ตัดครึ่ง
  ของ subtree ทิ้งในแต่ละขั้น
- อัลกอริทึม Euclidean สำหรับหา GCD (Greatest Common Divisor)

```c
/* นับว่าต้องหาร n ด้วย 2 กี่ครั้งจนเหลือ 1 -- จำลองแนวคิดการตัดครึ่งซ้ำๆ ของ Binary Search */
int count_halving_steps(int n) {
    int steps = 0;
    while (n > 1) {
        n = n / 2;
        steps++;
    }
    return steps;
}
```

ทดสอบ `count_halving_steps(1024)` จะได้ `10` เพราะ `1024 = 2^10` — สังเกตว่าถ้า `n` เพิ่มเป็น
2 เท่า (`2048`) ผลลัพธ์เพิ่มขึ้นแค่ `1` (`11`) เท่านั้น นี่คือคุณสมบัติที่ทำให้ O(log n) เป็น
Class ที่ดีที่สุดรองจาก O(1) — สามารถรับมือกับข้อมูลขนาดมหาศาลได้โดยแทบไม่กระทบเวลาทำงานเลย

## 24.5 Class ความซับซ้อน: O(n) และ O(n log n) (Step 189)

### O(n) — Linear Time

อัลกอริทึมที่เวลาทำงาน **เพิ่มขึ้นเป็นสัดส่วนโดยตรง** กับขนาดข้อมูลนำเข้า — เพิ่มข้อมูล 2 เท่า
เวลาทำงานก็เพิ่มเป็น 2 เท่าตาม

ตัวอย่าง:

- **Linear Search** (24.1) — Worst Case ต้องไล่ตรวจสอบทุกตัว
- การหาผลรวม/ค่ามากสุด/ค่าน้อยสุดของอาร์เรย์ — ต้องไล่อ่านทุกตัวอย่างน้อยหนึ่งครั้ง
- การ Traverse Linked List ทั้งเส้น (Part 19)
- การพิมพ์ Tree แบบ Inorder/Preorder/Postorder Traversal (Part 21) — เข้าเยี่ยมทุก node
  เพียงครั้งเดียว

```c
long sum_array(const int arr[], size_t n) {
    long total = 0;
    for (size_t i = 0; i < n; i++) {
        total += arr[i]; /* loop เดียว วิ่งตลอดความยาว n */
    }
    return total;
}
```

### O(n log n) — Linearithmic Time

Class นี้เกิดจากการทำงานแบบ O(log n) **ซ้ำ n ครั้ง** หรือทำงานแบบ O(n) **ซ้ำ log n ครั้ง**
เป็น Class ที่สำคัญมากเพราะเป็น "เพดานความเร็ว" ที่ดีที่สุดในทางทฤษฎีสำหรับอัลกอริทึม
Comparison-based Sorting ทั่วไป (พิสูจน์ได้ทางคณิตศาสตร์ว่าไม่มีอัลกอริทึมเรียงลำดับที่อาศัย
การเปรียบเทียบตัวต่อตัวใดเร็วกว่า O(n log n) ได้ในกรณีทั่วไป)

ตัวอย่างที่เรียนมาแล้วใน Part 23:

- **Merge Sort**: แบ่งปัญหาลง log n ระดับ (Divide) และแต่ละระดับใช้เวลารวม O(n) ในการ merge
  (Combine) → รวมเป็น O(n log n)
- **Quick Sort** (Average Case): แบ่งปัญหาแบบสุ่มลง log n ระดับโดยเฉลี่ย และแต่ละระดับใช้เวลา
  รวม O(n) ในการ partition → รวมเป็น O(n log n)

การมองภาพ Merge Sort ผ่าน Recursion Tree ช่วยให้เห็นที่มาของ n log n ชัดเจน:

```
ระดับ 0:  [n ตัว]                              -> ทำงาน O(n) รวมทั้งระดับ (merge สุดท้าย)
ระดับ 1:  [n/2]      [n/2]                     -> ทำงาน O(n) รวมทั้งระดับ (n/2 + n/2)
ระดับ 2:  [n/4][n/4] [n/4][n/4]                -> ทำงาน O(n) รวมทั้งระดับ
   ...
ระดับ log n: [1][1][1]...[1]                    -> ฐานของ Recursion

จำนวนระดับทั้งหมด = log₂(n)
แต่ละระดับทำงานรวม = O(n)
รวมทั้งหมด = O(n) × log₂(n) = O(n log n)
```

## 24.6 Class ความซับซ้อน: O(n²) และ O(2ⁿ) (Step 190)

### O(n²) — Quadratic Time

อัลกอริทึมที่มี **Loop ซ้อนกัน 2 ชั้น** โดยแต่ละชั้นวิ่งเป็นสัดส่วนกับ `n` ทั้งคู่ — เพิ่มข้อมูล
2 เท่า เวลาทำงานเพิ่มเป็น 4 เท่า

ตัวอย่างจาก Part 23:

- **Bubble Sort, Selection Sort, Insertion Sort** (Worst/Average Case) — loop นอกวิ่ง n รอบ
  loop ในวิ่งประมาณ n รอบเช่นกัน
- การพิมพ์ทุกคู่ที่เป็นไปได้ของสมาชิกในอาร์เรย์

```c
void print_all_pairs(const int arr[], size_t n) {
    for (size_t i = 0; i < n; i++) {      /* วิ่ง n รอบ */
        for (size_t j = 0; j < n; j++) {  /* วิ่ง n รอบ สำหรับทุกค่าของ i */
            printf("(%d,%d) ", arr[i], arr[j]);
        }
    }
    printf("\n");
}
```

จำนวนครั้งที่ `printf` ถูกเรียกคือ `n × n = n²` พอดี

### O(2ⁿ) — Exponential Time

อัลกอริทึมที่เวลาทำงาน **เพิ่มเป็นสองเท่าทุกครั้งที่ขนาดข้อมูลเพิ่มขึ้นแค่ 1** — เป็น Class
ที่แย่ที่สุดในบรรดา Class ที่ยังพอใช้งานได้จริงในขนาดปัญหาเล็กๆ แต่ **ระเบิด (blow up)**
อย่างรวดเร็วมากเมื่อ `n` โตขึ้น

ตัวอย่างคลาสสิกที่สุดคือ **Naive Recursive Fibonacci** (จะอธิบายลึกใน Part 25):

```c
long fib_naive(int n) {
    if (n <= 1) {
        return n;
    }
    return fib_naive(n - 1) + fib_naive(n - 2); /* เรียกตัวเอง 2 ครั้งทุกระดับ */
}
```

เพราะทุกการเรียก `fib_naive(n)` แตกออกเป็น 2 การเรียกย่อยเสมอ (`fib_naive(n-1)` และ
`fib_naive(n-2)`) จำนวนการเรียกทั้งหมดจึงโตแบบ Exponential ตามรูปร่าง Binary Tree:

| n | จำนวนครั้งที่เรียกฟังก์ชันจริง (นับจาก `fib_naive`) |
|---|---|
| 5 | 15 |
| 10 | 177 |
| 20 | 21,891 |
| 30 | ประมาณ 2.7 ล้านครั้ง |
| 40 | ประมาณ 331 ล้านครั้ง |
| 50 | ประมาณ 40,000 ล้านครั้ง (ใช้เวลาหลายนาทีถึงหลายชั่วโมง!) |

จะเห็นว่าจากอินพุตที่เพิ่มขึ้นทีละหน่วย เวลาทำงานเพิ่มขึ้นแบบก้าวกระโดดจนควบคุมไม่ได้ — นี่คือ
เหตุผลที่ต้องรู้จัก **Memoization และ Dynamic Programming** ซึ่งจะเรียนใน Part 25 เพื่อลด
ความซับซ้อนของปัญหาแบบนี้ให้เหลือ O(n) เท่านั้น

### สรุปตารางเปรียบเทียบทุก Class พร้อมตัวอย่างจริงจากหลักสูตรนี้

| Class | ชื่อเรียก | ตัวอย่างจากหลักสูตรนี้ | n=10 (ประมาณ) | n=1,000,000 (ประมาณ) |
|---|---|---|---|---|
| O(1) | Constant | เข้าถึงอาร์เรย์ผ่าน index | 1 | 1 |
| O(log n) | Logarithmic | Binary Search (24.2) | ~3 | ~20 |
| O(n) | Linear | Linear Search (24.1), sum_array | 10 | 1,000,000 |
| O(n log n) | Linearithmic | Merge Sort, Quick Sort (Part 23) | ~33 | ~20,000,000 |
| O(n²) | Quadratic | Bubble/Selection/Insertion Sort (Part 23) | 100 | 10¹² (นับล้านล้าน) |
| O(2ⁿ) | Exponential | Naive Recursive Fibonacci | 1,024 | มากเกินจะคำนวณได้ในเวลาที่สมเหตุสมผล |

ตารางนี้แสดงให้เห็นชัดว่าทำไมนักพัฒนาซอฟต์แวร์มืออาชีพถึงให้ความสำคัญกับการวิเคราะห์ Big-O
ก่อนเขียนโค้ดจริงกับข้อมูลขนาดใหญ่ — ความแตกต่างระหว่าง O(n log n) กับ O(n²) อาจหมายถึงความ
แตกต่างระหว่างโปรแกรมที่รันเสร็จใน 1 วินาที กับโปรแกรมที่ค้างไปเป็นชั่วโมง

### ความซับซ้อนของฟังก์ชันมาตรฐานที่ใช้บ่อยใน C

เวลาเขียนโค้ดจริง เรามักเรียกใช้ฟังก์ชันจาก Standard Library โดยไม่ทันสังเกตว่าแต่ละฟังก์ชัน
มีความซับซ้อนซ่อนอยู่เท่าไหร่ ตารางนี้สรุปฟังก์ชันที่ใช้บ่อยที่สุดในหลักสูตรนี้ไว้ให้อ้างอิง:

| ฟังก์ชัน | Header | Complexity | หมายเหตุ |
|---|---|---|---|
| `strlen(s)` | `<string.h>` | O(n) | ไล่หา `'\0'` ทีละไบต์ — เรียกซ้ำใน loop จะกลายเป็น O(n²) |
| `strcpy(dst, src)` | `<string.h>` | O(n) | n คือความยาวของ `src` |
| `strcmp(a, b)` | `<string.h>` | O(min(n, m)) | หยุดทันทีที่เจอไบต์ที่ไม่ตรงกัน หรือถึง `'\0'` |
| `malloc(size)` | `<stdlib.h>` | O(1) โดยเฉลี่ย (Amortized) | ขึ้นกับ Memory Allocator ภายใน แต่โดยทั่วไปถือเป็นค่าคงที่ |
| `qsort(...)` | `<stdlib.h>` | O(n log n) โดยเฉลี่ย | ตามที่อธิบายไว้ในหัวข้อ 23.8 |
| `bsearch(...)` | `<stdlib.h>` | O(log n) | ใช้หลักการเดียวกับ Binary Search ทุกประการ ต้องการข้อมูลเรียงแล้ว |
| การเข้าถึง element ของ Linked List ตำแหน่งที่ k | — | O(n) | ต่างจากอาร์เรย์ (O(1)) เพราะต้อง Traverse จากหัวไปทีละ node (Part 19) |

> **Amortized Complexity คืออะไร**: บางครั้งฟังก์ชันหนึ่งครั้งอาจใช้เวลานาน (เช่น `malloc`
> ที่ต้องขยาย Heap บางครั้งคราว หรือการเพิ่มสมาชิกใน Dynamic Array ที่บางครั้งต้องจองพื้นที่ใหม่
> ทั้งก้อนแล้วคัดลอกข้อมูลเก่าทั้งหมด) แต่ถ้า**เฉลี่ยต้นทุนของการทำงานหลายๆ ครั้งรวมกัน**แล้ว
> ต้นทุนเฉลี่ยต่อครั้งยังคงต่ำ (เช่น O(1)) เราจะเรียกว่า Amortized O(1) — เป็นแนวคิดที่สำคัญ
> มากเวลาวิเคราะห์โครงสร้างข้อมูลอย่าง Dynamic Array (`std::vector` ใน C++ ที่จะเรียนใน
> Module F) และ Hash Table (Part 22)

## 24.7 วิเคราะห์ความซับซ้อนของโค้ดด้วยการนับ Loop Iteration (Step 191)

ตอนนี้เรามาสร้างวิธีการที่เป็นระบบสำหรับวิเคราะห์ความซับซ้อนของโค้ดชิ้นใดก็ได้ หลักการพื้นฐาน
มีดังนี้:

### กฎพื้นฐาน 5 ข้อ

1. **คำสั่งพื้นฐาน (assignment, arithmetic, comparison)** ที่ไม่อยู่ใน loop → นับเป็น O(1)
2. **Loop ธรรมดา 1 ชั้น** ที่วิ่งตามขนาดข้อมูล `n` → นับเป็น O(n)
3. **Loop ซ้อนกัน** → คูณจำนวนรอบของแต่ละชั้นเข้าด้วยกัน
4. **Loop ที่ตัวแปรควบคุมคูณ/หารด้วยค่าคงที่ทุกรอบ** (เช่น `i *= 2` หรือ `i /= 2`) → นับเป็น
   O(log n) เสมอ
5. **คำสั่งที่เรียงต่อกัน (ไม่ซ้อนกัน)** → บวกความซับซ้อนของแต่ละส่วนเข้าด้วยกัน แล้วเก็บ
   เฉพาะเทอมที่โตเร็วที่สุด (ตามหลักการตัดเทอมเล็กทิ้งจากหัวข้อ 24.3)

### ตัวอย่างที่ 1: Loop เรียงต่อกัน

```c
void example1(const int arr[], size_t n) {
    for (size_t i = 0; i < n; i++) {        /* O(n) */
        printf("%d ", arr[i]);
    }

    for (size_t i = 0; i < n; i++) {        /* O(n) */
        for (size_t j = 0; j < n; j++) {    /* O(n) ซ้อนอยู่ข้างใน -> รวมเป็น O(n^2) */
            printf("%d ", arr[i] + arr[j]);
        }
    }
}
```

วิเคราะห์: loop แรกคือ O(n), loop ที่สอง (ซ้อนกัน) คือ O(n²) เพราะสองส่วนนี้ **เรียงต่อกัน
ไม่ได้ซ้อนกัน** จึง**บวก**ความซับซ้อนกัน: `O(n) + O(n²)` แล้วเก็บเทอมที่โตเร็วที่สุด
→ ผลลัพธ์สุดท้ายคือ **O(n²)**

### ตัวอย่างที่ 2: Loop ที่ขอบเขตไม่เท่ากับ n ตรงๆ

```c
void example2(const int arr[], size_t n) {
    for (size_t i = 0; i < n; i++) {          /* วิ่ง n รอบ */
        for (size_t j = i; j < n; j++) {      /* วิ่งลดลงเรื่อยๆ: n, n-1, n-2, ..., 1 */
            printf("%d ", arr[i] + arr[j]);
        }
    }
}
```

วิเคราะห์: จำนวนรอบรวมของ loop ในคือ `n + (n-1) + (n-2) + ... + 1` ซึ่งเป็นผลรวมทางคณิตศาสตร์
ที่เท่ากับ `n(n+1)/2` — เมื่อกระจายจะได้ `(n² + n) / 2` ตัดค่าคงที่ (1/2) และเทอมเล็ก (`n`)
ทิ้งตามกฎ Big-O → ผลลัพธ์คือ **O(n²)** เช่นกัน (นี่คือรูปแบบเดียวกับที่เกิดใน Bubble Sort
และ Selection Sort จาก Part 23 ที่ loop ในวิ่งสั้นลงเรื่อยๆ ทุกรอบของ loop นอก)

### ตัวอย่างที่ 3: Loop แบบคูณ/หาร (นำไปสู่ Logarithm)

```c
int example3(int n) {
    int count = 0;
    for (int i = 1; i < n; i = i * 2) {   /* i: 1, 2, 4, 8, 16, ... จนเกิน n */
        count++;
    }
    return count;
}
```

วิเคราะห์: ตัวแปร `i` เพิ่มค่าแบบ **คูณ 2** ทุกรอบ (ไม่ใช่บวกทีละ 1) คำถามคือ "ต้องคูณ 2
กี่ครั้งจนกว่า `i` จะมีค่าเกิน `n`" ซึ่งตามนิยามทางคณิตศาสตร์ของ Logarithm คือ `log₂(n)`
พอดี → ผลลัพธ์คือ **O(log n)** (รูปแบบเดียวกับที่เกิดใน Binary Search)

### ตัวอย่างที่ 4: Recursive Call

การวิเคราะห์ Recursive Function ใช้หลักการนับ **จำนวนครั้งที่ฟังก์ชันถูกเรียก** คูณด้วย
**งานที่ทำในแต่ละครั้งที่เรียก (ไม่รวมงานของการเรียกซ้ำ)**:

```c
long fib_naive(int n) {
    if (n <= 1) {
        return n;                              /* งานฐาน: O(1) */
    }
    return fib_naive(n - 1) + fib_naive(n - 2); /* เรียกตัวเอง 2 ครั้ง + งาน O(1) */
}
```

ให้ `T(n)` แทนจำนวนการเรียกฟังก์ชันทั้งหมดเมื่ออินพุตคือ `n`:

```
T(n) = T(n-1) + T(n-2) + 1   (สมการ Recurrence)
```

สมการนี้มีรูปร่างคล้ายกับลำดับ Fibonacci เอง และสามารถพิสูจน์ได้ว่า `T(n)` เติบโตในอัตรา
**O(2ⁿ)** (แม่นยำกว่าคือ O(φⁿ) โดย φ ≈ 1.618 แต่ในทางปฏิบัติมักประมาณเป็น O(2ⁿ) เพราะยังคง
เป็น Exponential เหมือนกัน และเข้าใจง่ายกว่า) ซึ่งตรงกับตัวเลขที่นับได้จริงในตารางของหัวข้อ
24.6 ก่อนหน้านี้

### เทคนิคเร็ว: มองรูปร่างของ Loop แล้วเทียบกับ Pattern มาตรฐาน

| ลักษณะของโค้ด | Complexity |
|---|---|
| ไม่มี loop, ไม่มี recursion | O(1) |
| Loop เดี่ยว วิ่งเต็ม n | O(n) |
| Loop ซ้อนกัน 2 ชั้น วิ่งเต็มทั้งคู่ | O(n²) |
| Loop ซ้อนกัน k ชั้น วิ่งเต็มทุกชั้น | O(nᵏ) |
| Loop ที่ตัวแปรคูณ/หารด้วยค่าคงที่ทุกรอบ | O(log n) |
| Loop เดี่ยว + เรียก loop อีกตัวที่เป็น O(log n) ในทุกรอบ | O(n log n) |
| Recursive function ที่แตกเป็น 2 กิ่งขึ้นไปโดยไม่มี Memoization | O(2ⁿ) หรือแย่กว่า |

## 24.8 Best Case, Average Case และ Worst Case (Step 192)

จากตัวอย่างทั้งหมดที่ผ่านมา เราเห็นแล้วว่าอัลกอริทึมตัวเดียวกันอาจมีความซับซ้อนต่างกันได้
ขึ้นอยู่กับ "ลักษณะของข้อมูลนำเข้า" — จึงต้องแยกวิเคราะห์เป็น 3 กรณีเสมอ:

- **Best Case**: สถานการณ์ที่ดีที่สุดที่จะเกิดขึ้นได้ — มักไม่ค่อยมีประโยชน์ในการตัดสินใจ
  ออกแบบระบบจริง เพราะเราไม่ควรวางแผนโดยหวังว่าจะได้เจอกรณีที่ดีที่สุดเสมอ
- **Worst Case**: สถานการณ์ที่แย่ที่สุดที่จะเกิดขึ้นได้ — สำคัญที่สุดสำหรับระบบที่ต้องการ
  **การรับประกันประสิทธิภาพ** (เช่นระบบ Real-time, ระบบที่มี SLA/Service Level Agreement)
  เพราะต้องมั่นใจว่าระบบจะไม่ช้าเกินขอบเขตที่ยอมรับได้ ไม่ว่าอินพุตจะเป็นอย่างไร
- **Average Case**: ค่าเฉลี่ยเมื่อพิจารณาอินพุตทุกแบบที่เป็นไปได้ตามการกระจายทางสถิติ (มักสมมติ
  ว่าทุกอินพุตมีโอกาสเกิดขึ้นเท่ากัน) — เป็นตัวเลขที่สะท้อนพฤติกรรม "ทั่วไปในการใช้งานจริง"
  ได้ดีที่สุด แต่คำนวณยากกว่า Worst Case มาก (ต้องใช้ความน่าจะเป็นและสถิติ)

### ตารางสรุปกรณีศึกษาจากอัลกอริทึมที่เรียนมาแล้ว

| อัลกอริทึม | Best Case | เกิดขึ้นเมื่อไหร่ | Worst Case | เกิดขึ้นเมื่อไหร่ |
|---|---|---|---|---|
| Linear Search | O(1) | เป้าหมายอยู่ตำแหน่งแรก | O(n) | เป้าหมายอยู่ตำแหน่งสุดท้าย/ไม่พบเลย |
| Binary Search | O(1) | เป้าหมายอยู่ตรงกลางพอดีในรอบแรก | O(log n) | เป้าหมายอยู่ที่ขอบ/ไม่พบเลย |
| Insertion Sort | O(n) | ข้อมูลเรียงอยู่แล้ว | O(n²) | ข้อมูลเรียงกลับด้าน (มากไปน้อยเมื่อต้องการน้อยไปมาก) |
| Bubble Sort (มี optimization) | O(n) | ข้อมูลเรียงอยู่แล้ว | O(n²) | ข้อมูลเรียงกลับด้านสมบูรณ์ |
| Quick Sort (Lomuto, pivot=ตัวสุดท้าย) | O(n log n) | การแบ่งสมดุลทุกครั้ง | O(n²) | ข้อมูลเรียงอยู่แล้ว (หรือเรียงกลับด้าน) ทำให้แบ่งไม่สมดุลซ้ำๆ |

จุดที่น่าสนใจมากคือ **Quick Sort กับข้อมูลที่เรียงอยู่แล้ว**: ถ้าเราส่งอาร์เรย์ที่เรียงสมบูรณ์
แล้วเข้าไปใน `quick_sort()` จาก Part 23 (ที่เลือก Pivot เป็นตัวสุดท้ายเสมอ) การ Partition
แต่ละรอบจะได้กลุ่ม "น้อยกว่า Pivot" ขนาด n-1 ตัว กับกลุ่ม "มากกว่า Pivot" ขนาด 0 ตัวเสมอ —
ทำให้ Recursion ลึกถึง n ระดับ แทนที่จะเป็น log n ระดับตามที่หวัง กลายเป็น O(n²) ทันที นี่คือ
เหตุผลที่ระบบจริงมักใช้เทคนิค **Randomized Pivot** หรือ **Median-of-Three** เพื่อลดโอกาส
เจอ Worst Case แบบนี้ให้เหลือน้อยที่สุด

### เมื่อไหร่ควรสนใจ Case ไหน

| สถานการณ์งานจริง | ควรสนใจ Case ไหน |
|---|---|
| ระบบควบคุมอุปกรณ์ทางการแพทย์/การบิน (Real-time, Safety-critical) | Worst Case เท่านั้น — ต้องรับประกันเวลาตอบสนองสูงสุด |
| Web Server ที่รับ Request จากผู้ใช้จำนวนมาก | Average Case เป็นหลัก แต่ต้องรู้ Worst Case ไว้ป้องกัน Attack (เช่น Algorithmic Complexity Attack ที่จงใจส่งอินพุตให้ตกไปอยู่ใน Worst Case) |
| Batch Processing ข้อมูลที่รู้ลักษณะข้อมูลล่วงหน้า (เช่นข้อมูลใกล้เรียงอยู่แล้วเสมอ) | Best/Average Case ของอัลกอริทึมที่เหมาะกับลักษณะข้อมูลนั้นโดยเฉพาะ (เช่น Insertion Sort) |
| การเตรียมสัมภาษณ์งานสาย Software Engineer | ต้องตอบได้ทั้ง 3 Case พร้อมเหตุผลเสมอ (จะฝึกเจาะลึกใน Part 119) |

## ข้อผิดพลาดที่พบบ่อย (Common Pitfalls)

1. **ใช้ Binary Search กับอาร์เรย์ที่ยังไม่ได้เรียง** โดยไม่รู้ตัว ทำให้ได้ผลลัพธ์ "ไม่พบ"
   ทั้งที่ค่านั้นมีอยู่จริงในอาร์เรย์ — ต้องตรวจสอบให้แน่ใจเสมอว่าข้อมูลเรียงแล้วก่อนเรียกใช้
   Binary Search (หรือเขียน assertion ตรวจสอบไว้ในโหมด Debug)

2. **เขียน `mid = (low + high) / 2` แทน `mid = low + (high - low) / 2`** ซึ่งดูเหมือนเทียบเท่า
   กันทางคณิตศาสตร์ แต่เสี่ยง Integer Overflow เมื่อ `low` และ `high` มีค่าใกล้ขอบเขตสูงสุด
   ของชนิดข้อมูล (พบได้จริงในระบบที่ทำงานกับอาร์เรย์ขนาดใหญ่มากถึงระดับพันล้านสมาชิก)

3. **สับสนระหว่าง "จำนวนครั้งที่ Loop ทำงาน" กับ "Big-O ของ Loop นั้น"** เช่นคิดว่า loop ที่
   วิ่ง `n + 5` รอบมีความซับซ้อนต่างจาก loop ที่วิ่ง `n` รอบพอดี — ทั้งสองแบบคือ **O(n)** เท่ากัน
   เพราะ Big-O สนใจแค่แนวโน้มการเติบโตเมื่อ `n` มีค่ามากๆ ไม่ใช่ตัวเลขที่แน่นอน

4. **ลืมพิจารณา Loop ที่ซ่อนอยู่ในฟังก์ชันที่เรียกใช้** เช่นเรียก `strlen()` ภายใน loop
   (`for (int i = 0; i < strlen(s); i++)`) — `strlen()` เองมีความซับซ้อน O(n) (ต้องไล่หา
   `'\0'`) ถ้าเรียกซ้ำในทุกรอบของ loop ที่วิ่ง n รอบ จะกลายเป็น O(n²) โดยไม่รู้ตัว! ควรเก็บ
   ค่า `strlen(s)` ไว้ในตัวแปรก่อนเข้า loop เสมอ

5. **สรุปว่าอัลกอริทึมที่ Big-O ดีกว่าจะเร็วกว่าเสมอในทุกกรณี** เช่นคิดว่า O(n log n) เร็วกว่า
   O(n²) เสมอ — แต่ Big-O บอกแค่ **แนวโน้มเมื่อ n มีค่ามากพอ** เท่านั้น สำหรับ `n` ขนาดเล็กมาก
   (เช่น n < 10-20) อัลกอริทึม O(n²) ที่มี Constant Factor เล็กกว่าอาจเร็วกว่า O(n log n)
   ที่มี Overhead สูงกว่าในทางปฏิบัติจริงได้ (ตามที่อธิบายไว้ในหัวข้อ 23.8)

6. **ไม่แยกวิเคราะห์ Best/Average/Worst Case ให้ชัดเจน** แล้วพูดคลุมเครือว่า "อัลกอริทึมนี้คือ
   O(n)" โดยไม่ระบุว่าหมายถึงกรณีไหน ทำให้สื่อสารผิดพลาดในทีมพัฒนา หรือตอบคำถามสัมภาษณ์งาน
   ไม่ครบถ้วน

## แบบฝึกหัดท้ายบท

1. เขียนฟังก์ชัน `long linear_search_all(const int arr[], size_t n, int target, size_t
   result_indices[])` ที่ค้นหา **ทุกตำแหน่ง** ที่มีค่าเท่ากับ `target` (ไม่ใช่แค่ตำแหน่งแรก)
   แล้วบอกว่าฟังก์ชันนี้มีความซับซ้อนเป็น O(อะไร)

2. ดัดแปลง `binary_search_recursive()` ให้พิมพ์ค่า `low`, `high`, `mid` ออกมาทุกรอบที่เรียก
   แล้วทดสอบกับอาร์เรย์ตัวอย่างในบทเรียน เพื่อยืนยัน Trace ที่แสดงไว้ในหัวข้อ 24.2

3. วิเคราะห์ความซับซ้อนของโค้ดต่อไปนี้ด้วยตัวเอง (เขียนคำตอบเป็น Big-O พร้อมอธิบายเหตุผล):
   ```c
   void mystery(const int arr[], size_t n) {
       for (size_t i = 0; i < n; i++) {
           for (size_t j = 0; j < n; j++) {
               for (size_t k = 0; k < n; k++) {
                   printf("%d ", arr[i] + arr[j] + arr[k]);
               }
           }
       }
   }
   ```

4. เขียนโปรแกรมที่วัดเวลาจริง (ใช้ `clock()` จาก `<time.h>`) เปรียบเทียบ Linear Search กับ
   Binary Search บนอาร์เรย์ที่เรียงแล้วขนาด 1,000,000 ตัว ค้นหาค่าที่อยู่ตำแหน่งสุดท้าย
   แล้วรายงานเวลาที่ใช้ของทั้งสองวิธี

5. จงบอกว่าฟังก์ชัน `count_halving_steps()` จากหัวข้อ 24.4 มี Best Case และ Worst Case
   ต่างกันหรือไม่ อย่างไร (คำใบ้: ลองพิจารณา `n = 0`, `n = 1` และ `n` ที่มีค่ามาก)

6. เขียนฟังก์ชัน `interpolation_search()` ซึ่งเป็นการค้นหาที่ปรับปรุงจาก Binary Search โดย
   ประมาณตำแหน่งของเป้าหมายจากค่าที่ขอบทั้งสองด้าน (เหมาะกับข้อมูลที่กระจายตัวสม่ำเสมอ) แล้ว
   ค้นหาข้อมูลเพิ่มเติมด้วยตัวเองว่าเทคนิคนี้มี Best/Average/Worst Case เป็นอย่างไร

### แนวทางเฉลยข้อ 1

```c
/* ============================================================
 * ชื่อไฟล์:     linear_search_all.c
 * คำอธิบาย:     ค้นหาทุกตำแหน่งที่มีค่าเท่ากับ target ในอาร์เรย์
 * ============================================================ */
#include <stdio.h>
#include <stddef.h>

#define ARRAY_SIZE 10

size_t linear_search_all(const int arr[], size_t n, int target,
                          size_t result_indices[]);

int main(void) {
    int data[ARRAY_SIZE] = {4, 7, 4, 2, 4, 9, 1, 4, 6, 4};
    size_t indices[ARRAY_SIZE]; /* จองพื้นที่สูงสุดเท่าที่เป็นไปได้ */

    int target = 4;
    size_t found_count = linear_search_all(data, ARRAY_SIZE, target, indices);

    printf("พบค่า %d ทั้งหมด %zu ตำแหน่ง: ", target, found_count);
    for (size_t i = 0; i < found_count; i++) {
        printf("%zu ", indices[i]);
    }
    printf("\n");

    return 0;
}

size_t linear_search_all(const int arr[], size_t n, int target,
                          size_t result_indices[]) {
    size_t count = 0;

    for (size_t i = 0; i < n; i++) {
        if (arr[i] == target) {
            result_indices[count] = i;
            count++;
        }
    }

    return count;
}
```

ผลลัพธ์:

```
พบค่า 4 ทั้งหมด 5 ตำแหน่ง: 0 2 4 7 9
```

**วิเคราะห์ความซับซ้อน**: ฟังก์ชันนี้ยังคงเป็น **O(n)** เหมือน Linear Search ธรรมดา เพราะ
ไม่ว่าจะพบเป้าหมายกี่ตำแหน่งก็ตาม เรายังคงต้องไล่ตรวจสอบสมาชิกทุกตัวในอาร์เรย์เพียงรอบเดียว
(ไม่มีการวนซ้ำหรือค้นหาซ้ำ) การเขียนผลลัพธ์ลง `result_indices[]` เป็นงาน O(1) ต่อครั้งที่พบ
ค่า จึงไม่เปลี่ยนแนวโน้มความซับซ้อนโดยรวม — ต่างจาก `linear_search()` เดิมที่หยุดทันทีที่เจอ
ตัวแรก (Best Case O(1) ได้) ฟังก์ชันนี้ **ต้องไล่ครบทุกตัวเสมอ** ไม่ว่าจะเจอเร็วแค่ไหน เพราะ
ต้องมั่นใจว่าไม่พลาดตำแหน่งที่เหลือ ดังนั้น Best Case และ Worst Case ของฟังก์ชันนี้จึงเท่ากัน
คือ **Θ(n)** พอดี

### แนวทางเฉลยข้อ 3

```
วิเคราะห์:
- loop ที่ i: วิ่ง n รอบ
- loop ที่ j (ซ้อนใน i): วิ่ง n รอบ สำหรับทุกค่าของ i
- loop ที่ k (ซ้อนใน j): วิ่ง n รอบ สำหรับทุกค่าของ j

จำนวนครั้งที่ printf ถูกเรียกทั้งหมด = n * n * n = n^3

คำตอบ: ความซับซ้อนของฟังก์ชันนี้คือ O(n^3) (Cubic Time)
เพราะมี loop ซ้อนกัน 3 ชั้น โดยแต่ละชั้นวิ่งเต็มความยาว n ทั้งหมด
ตรงตาม Pattern "Loop ซ้อนกัน k ชั้น วิ่งเต็มทุกชั้น -> O(n^k)" จากตารางในหัวข้อ 24.7 (k=3)
```

### แนวทางเฉลยข้อ 5

```c
/* ============================================================
 * ชื่อไฟล์:     halving_cases.c
 * คำอธิบาย:     วิเคราะห์ Best/Worst Case ของ count_halving_steps()
 * ============================================================ */
#include <stdio.h>

int count_halving_steps(int n);

int main(void) {
    int test_values[] = {0, 1, 2, 3, 1024, 1000000};
    int count = (int)(sizeof(test_values) / sizeof(test_values[0]));

    for (int i = 0; i < count; i++) {
        int n = test_values[i];
        printf("count_halving_steps(%7d) = %d\n", n, count_halving_steps(n));
    }

    return 0;
}

int count_halving_steps(int n) {
    int steps = 0;
    while (n > 1) {
        n = n / 2;
        steps++;
    }
    return steps;
}
```

ผลลัพธ์:

```
count_halving_steps(      0) = 0
count_halving_steps(      1) = 0
count_halving_steps(      2) = 1
count_halving_steps(      3) = 1
count_halving_steps(   1024) = 10
count_halving_steps(1000000) = 19
```

**คำอธิบาย**: `count_halving_steps()` แทบไม่มีความแตกต่างระหว่าง Best Case กับ Worst Case
เลย เพราะ loop เงื่อนไข `n > 1` จะทำงานตามจำนวนครั้งที่แน่นอนทางคณิตศาสตร์เสมอ (คือ
⌊log₂(n)⌋ พอดี ไม่ขึ้นกับ "ค่าที่กำลังค้นหา" แบบ Binary Search) กรณีพิเศษเดียวคือเมื่อ
`n = 0` หรือ `n = 1` ที่ loop ไม่ทำงานเลย (0 รอบ) ซึ่งถือเป็นทั้ง Best Case และ Worst Case
ไปพร้อมกันในกรณีขอบนี้ — พูดได้ว่าฟังก์ชันนี้มีความซับซ้อนแบบ **Θ(log n)** (Big-Theta) คือ
Best Case และ Worst Case เท่ากันเป๊ะ ต่างจาก Binary Search ที่ Best Case (O(1), เจอที่ mid
พอดี) กับ Worst Case (O(log n), ต้องหาจนสุดขอบเขต) ต่างกันอย่างชัดเจน — นี่คือตัวอย่างที่ดี
ที่แสดงว่าอัลกอริทึมสอง Class เดียวกัน (Logarithmic) อาจมีพฤติกรรม Best/Worst Case ต่างกัน
ได้ ขึ้นอยู่กับว่าผลลัพธ์ขึ้นกับ "ค่าที่ค้นหา" (แบบ Binary Search) หรือขึ้นกับ "ขนาดของ n
ล้วนๆ" (แบบ count_halving_steps)

- เขียนและเข้าใจ **Linear Search** ที่ใช้ได้กับข้อมูลทุกแบบ และ **Binary Search** ที่เร็วกว่า
  มากแต่ต้องการข้อมูลที่เรียงลำดับแล้วเท่านั้น พร้อมเข้าใจเหตุผลเชิงตรรกะว่าทำไม

  ทำงาน ไม่ใช่เวลาที่แน่นอน พร้อมรู้จัก Big-Omega และ Big-Theta

  Call
