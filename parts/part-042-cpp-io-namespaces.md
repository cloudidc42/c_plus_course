## 42.1 Stream คืออะไร: `std::cout`/`std::cin`/`std::cerr` เทียบกับ `printf`/`scanf` (Step 329)

### จาก Format String สู่ Stream

ตลอด Module A–C เราใช้ `printf`/`scanf` ทำงานกับ **Format String** (`%d`, `%s`, `%f`) ที่ต้อง
จับคู่ให้ตรงกับชนิดข้อมูลของ argument ด้วยมือเสมอ (ทบทวน Part 3) ถ้าจับคู่ผิด เช่น
`printf("%d\n", some_double)` compiler ของ C จะแค่**เตือน** (Warning) แต่ยังคอมไพล์ผ่านและ
ทำงานผิดพลาดตอนรันจริง ซึ่งเป็นแหล่งบั๊กที่พบบ่อยมาก

C++ แก้ปัญหานี้ด้วยแนวคิดที่เรียกว่า **Stream** — object ที่แทน "ช่องทางไหลของข้อมูล" ไม่ว่าจะ
เป็นคีย์บอร์ด จอภาพ ไฟล์ หรือแม้แต่ string ในหน่วยความจำ ไลบรารีที่ให้บริการ stream คือ
`<iostream>` ซึ่งมี object สำเร็จรูป 3 ตัวที่สอดคล้องกับ 3 ช่องทางมาตรฐานของ C ที่เรียนมาแล้ว
(`stdout`, `stdin`, `stderr` จาก Part 3):

| Object ของ C++ | เทียบเท่ากับของ C | ใช้ทำอะไร |
|---|---|---|
| `std::cout` | `stdout` (คู่กับ `printf`) | พิมพ์ผลลัพธ์ปกติออกหน้าจอ |
| `std::cin` | `stdin` (คู่กับ `scanf`) | รับข้อมูลจากคีย์บอร์ด |
| `std::cerr` | `stderr` | พิมพ์ข้อความ error (ไม่ buffer ส่งออกทันที) |
| `std::clog` | `stderr` (แบบมี buffer) | พิมพ์ log ที่ไม่จำเป็นต้องเห็นทันที (ใช้น้อยกว่า `cerr`) |

### ทำไม Stream ถึง Type-Safe กว่า

จุดต่างที่สำคัญที่สุด: `std::cout` **ไม่ต้องระบุ format specifier เลย** เพราะ C++ ใช้กลไกที่
เรียกว่า **Operator Overloading** (จะเรียนเจาะลึกใน Part 51) ทำให้ตัวดำเนินการ `<<` มีพฤติกรรม
ต่างกันไปโดยอัตโนมัติตาม **ชนิดข้อมูล** ของค่าที่ส่งเข้าไป — คอมไพเลอร์รู้เองว่าค่าที่ส่งเข้ามา
เป็น `int`, `double`, `char`, หรือ `std::string` แล้วเลือกวิธีพิมพ์ที่ถูกต้องให้อัตโนมัติ
**ไม่มีทางเกิดปัญหา "จับคู่ format specifier ผิดชนิด" แบบ `printf` ได้อีกต่อไป** เพราะไม่มี
format specifier ให้จับคู่ผิดตั้งแต่แรก

```cpp
#include <iostream>

int main() {
    int age = 25;
    double height = 172.5;
    char grade = 'A';

    std::cout << "อายุ: " << age << " ปี\n";
    std::cout << "ส่วนสูง: " << height << " ซม.\n";
    std::cout << "เกรด: " << grade << '\n';

    // chaining หลายค่าในบรรทัดเดียว
    std::cout << "สรุป: อายุ " << age << ", สูง " << height << ", เกรด " << grade << '\n';

    return 0;
}
```

```
อายุ: 25 ปี
ส่วนสูง: 172.5 ซม.
เกรด: A
สรุป: อายุ 25, สูง 172.5, เกรด A
```

### ตารางเปรียบเทียบ `printf`/`scanf` กับ `cout`/`cin` โดยละเอียด

| ประเด็น | `printf`/`scanf` (C) | `std::cout`/`std::cin` (C++) |
|---|---|---|
| การระบุชนิดข้อมูล | ต้องระบุ format specifier เอง (`%d`, `%s`, ...) | ไม่ต้องระบุ คอมไพเลอร์ตรวจชนิดข้อมูลให้อัตโนมัติ |
| ความปลอดภัยเมื่อชนิดข้อมูลไม่ตรง | UB ถ้าจับคู่ผิด (compiler เตือนได้แค่บางกรณี) | เป็นไปไม่ได้ที่จะจับคู่ผิด เพราะไม่มี specifier |
| การต่อค่าหลายตัว | ต้องใส่ทุกตัวใน argument เดียวของ `printf` | ต่อด้วย `<<` ได้เรื่อยๆ (chaining) |
| การขยายให้รองรับชนิดข้อมูลใหม่ | ทำไม่ได้ (compiler กำหนดตายตัว) | ทำได้ผ่าน Operator Overloading (Part 51) |
| ความเร็ว | เร็วกว่าเล็กน้อยโดยทั่วไป | ช้ากว่าเล็กน้อย (มี overhead ของ stream state) แต่ปลอดภัยกว่ามาก |
| ใช้กับไฟล์ได้ไหม | ใช้ `fprintf`/`fscanf` แยกชุดฟังก์ชัน | ใช้ stream ชนิดอื่น (`std::ofstream`/`std::ifstream`) หลักการเดียวกันทุกประการ |

> **ข้อสังเกตสำคัญ**: `printf`/`scanf` ยังใช้งานได้ปกติใน C++ (ทบทวนจาก Part 41 หัวข้อ 41.8)
> และในบางสถานการณ์ที่ต้องการความเร็วสูงสุดหรือ format ที่ซับซ้อนมาก โปรแกรมเมอร์ C++ มือ
> อาชีพบางคนก็ยังเลือกใช้ `printf` อยู่ แต่ **ตลอดหลักสูตรนี้ตั้งแต่ Module D เป็นต้นไป เราจะใช้
> `std::cout`/`std::cin` เป็นมาตรฐานหลัก** เพราะปลอดภัยกว่าและเข้ากับ Modern C++ Style มากกว่า

## 42.2 Stream Insertion (`<<`) และ Extraction (`>>`) Operator เจาะลึก (Step 330)

### ทิศทางของลูกศรบอกทิศทางข้อมูล

สังเกตว่าตัวดำเนินการทั้งสองตัวเป็น **ลูกศรชี้ทิศทาง** ซึ่งไม่ใช่เรื่องบังเอิญ — ทิศทางของลูกศร
บอกทิศทางการไหลของข้อมูลอย่างตรงไปตรงมา:

- **`<<` (Insertion)**: ข้อมูล**ไหลเข้าไปใน** stream เช่น `std::cout << x` คือ "ส่ง x เข้าไปใน
  cout" (แล้ว cout พิมพ์ออกจอ)
- **`>>` (Extraction)**: ข้อมูล**ไหลออกจาก** stream เช่น `std::cin >> x` คือ "ดึงค่าออกมาจาก
  cin ใส่ตัวแปร x"

จำง่ายๆ ว่า **ลูกศรชี้ไปทางไหน ข้อมูลก็ไหลไปทางนั้น** — `cout << x` ลูกศรชี้เข้า cout, `cin >>
x` ลูกศรชี้เข้า x

### `>>` รับได้หลายตัวต่อกันเหมือน `<<`

```cpp
#include <iostream>

int main() {
    int a = 0;
    int b = 0;

    std::cout << "ป้อนตัวเลขสองตัว: ";
    std::cin >> a >> b;  // extraction operator รับได้หลายตัวต่อกันเหมือน insertion

    std::cout << "ผลรวม = " << (a + b) << '\n';
    return 0;
}
```

```
ป้อนตัวเลขสองตัว: 7 8
ผลรวม = 15
```

`std::cin >> a >> b` ทำงานเหมือนกับ `scanf("%d %d", &a, &b)` ทุกประการในผลลัพธ์ แต่สังเกตว่า
**ไม่ต้องใช้ `&` นำหน้าตัวแปรเลย** — เหตุผลคือ `std::cin >> a` รับ `a` แบบ **reference**
ไม่ใช่ pointer แบบที่ `scanf` ต้องการ (จะเรียนเรื่อง reference อย่างละเอียดใน **Part 43** ซึ่ง
เป็น Part ถัดจากนี้พอดี) `>>` จะข้าม whitespace (ช่องว่าง, tab, newline) ให้อัตโนมัติก่อนเริ่ม
อ่านค่าเสมอ เหมือนกับที่ `%d` ของ `scanf` ทำ

### ทำไมต้อง `std::cin >> a >> b` ไม่ใช่ `(std::cin >> a) >> b` แยกกัน

จริงๆ แล้ว `std::cin >> a >> b` เทียบเท่ากับ `(std::cin >> a) >> b` เป๊ะ — เพราะ `>>` เป็น
Operator ที่ **คืนค่า reference กลับไปยัง stream ตัวเดิม** (คือคืน `std::cin` กลับมาอีกที) ทำให้
เขียนต่อกันเป็นลูกโซ่ได้เรื่อยๆ นี่คือกลไกเดียวกับที่ `std::cout << a << b << c` ทำงานได้ (แต่ละ
`<<` คืน reference ของ `std::cout` กลับมาให้ตัวถัดไปใช้ต่อ) รายละเอียดว่า "การคืน reference"
ทำงานอย่างไรเบื้องหลังจะชัดเจนมากขึ้นหลังเรียน Part 43

## 42.3 จัดการ Fail State ของ `std::cin` (Step 331)

### ปัญหา: ผู้ใช้ป้อนข้อมูลผิดชนิด

ถ้าโปรแกรมต้องการ `int` แต่ผู้ใช้พิมพ์ตัวอักษรเข้ามา `std::cin` จะเข้าสู่สถานะที่เรียกว่า
**fail state** — ค่าที่รับมาไม่ถูกต้อง (ตัวแปรเป้าหมายจะถูกตั้งเป็น `0`) และ **stream จะไม่
ยอมรับข้อมูลอะไรอีกเลย** จนกว่าจะล้างสถานะนี้ก่อน (คล้ายกับ error state ที่ `scanf` คืนค่า
จำนวน argument ที่อ่านสำเร็จน้อยกว่าที่คาดหวัง แต่ `std::cin` มีกลไกจัดการที่ชัดเจนกว่า)

```cpp
#include <iostream>
#include <limits>

int main() {
    int number = 0;

    std::cout << "ป้อนตัวเลข: ";
    while (!(std::cin >> number)) {
        std::cout << "ข้อมูลไม่ใช่ตัวเลข กรุณาป้อนใหม่: ";
        std::cin.clear();  // ล้างสถานะ fail ของ stream
        std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');  // ทิ้งข้อมูลขยะที่เหลือในบรรทัด
    }

    std::cout << "คุณป้อน: " << number << '\n';
    return 0;
}
```

ทดสอบด้วยการป้อน `abc` ก่อนแล้วตามด้วย `42`:

```
ป้อนตัวเลข: ข้อมูลไม่ใช่ตัวเลข กรุณาป้อนใหม่: คุณป้อน: 42
```

### อ่านโค้ดทีละขั้น

1. **`std::cin >> number` ใน `while (!(...))`**: `std::cin >> number` คืนค่าที่แปลงเป็น
   `bool` ได้ — `true` ถ้าอ่านสำเร็จ, `false` ถ้าล้มเหลว (เข้าสู่ fail state) ใส่ `!` ข้างหน้า
   เพื่อวนลูปต่อไปเรื่อยๆ **ตราบใดที่ยังอ่านไม่สำเร็จ**
2. **`std::cin.clear()`**: เมื่อ stream เข้าสู่ fail state มันจะปฏิเสธการอ่านค่าใดๆ ต่อไปอีก
   ตลอดไป จนกว่าจะเรียก `.clear()` เพื่อล้าง flag ข้อผิดพลาดนี้ทิ้งก่อน
3. **`std::cin.ignore(...)`**: แค่ `.clear()` อย่างเดียวไม่พอ เพราะตัวอักษรผิดพลาดที่ผู้ใช้พิมพ์
   เข้ามา (เช่น `"abc"`) **ยังค้างอยู่ใน buffer ของ stream** ถ้าไม่ทิ้งออกไปก่อน การอ่านครั้ง
   ถัดไปจะไปเจอตัวอักษรเดิมที่ผิดอยู่ดี ทำให้เข้า loop ไม่รู้จบ `.ignore()` สั่งให้ทิ้งอักขระ
   ทั้งหมดจนกว่าจะเจอ `'\n'` (จบบรรทัด) — `std::numeric_limits<std::streamsize>::max()` คือ
   "จำนวนอักขระมากที่สุดเท่าที่เป็นไปได้" ป้องกันกรณีที่บรรทัดยาวผิดปกติ

> **กฎทองของหัวข้อนี้**: ทุกครั้งที่ตรวจสอบว่า `std::cin` อ่านล้มเหลว ต้องเรียกทั้ง `.clear()`
> **และ** `.ignore()` เสมอคู่กัน ขาดอันใดอันหนึ่งไปโปรแกรมจะทำงานผิดพลาดหรือค้างเป็น infinite
> loop ทันที

## 42.4 `std::cerr`: ช่องทางแยกสำหรับข้อความ Error (Step 331 ต่อ)

ทบทวน Part 3 และ Part 16: `stderr` คือช่องทางแยกจาก `stdout` โดยเฉพาะสำหรับข้อความ error
เหตุผลสำคัญคือ **`stderr` ไม่ถูก buffer และไม่ถูก redirect ไปพร้อมกับ `stdout`** เมื่อผู้ใช้
เขียน script ที่ redirect ผลลัพธ์ปกติไปเก็บไฟล์ (เช่น `./program > output.txt`) ข้อความ error
จาก `stderr` จะยังคงแสดงบนหน้าจอให้เห็นทันที ไม่ถูกเก็บปนไปกับผลลัพธ์ปกติ

```cpp
#include <iostream>

int divide_safe(int a, int b, bool *ok) {
    if (b == 0) {
        std::cerr << "Error: หารด้วยศูนย์ไม่ได้\n";
        *ok = false;
        return 0;
    }
    *ok = true;
    return a / b;
}

int main() {
    bool ok = false;
    int result = divide_safe(10, 0, &ok);
    if (ok) {
        std::cout << "ผลลัพธ์ = " << result << '\n';
    }
    return 0;
}
```

```
Error: หารด้วยศูนย์ไม่ได้
```

> **แนวทางปฏิบัติที่ดี**: ตลอดหลักสูตรนี้ตั้งแต่ Module D เป็นต้นไป ให้ใช้ `std::cout` สำหรับ
> ผลลัพธ์ปกติที่โปรแกรมตั้งใจส่งออก และใช้ `std::cerr` สำหรับข้อความ error/warning/diagnostic
> เท่านั้น เช่นเดียวกับหลักการที่ยึดถือมาตลอด Module A–C

## 42.5 Namespace คืออะไร และทำไมต้องมี (Step 332)

### ปัญหา: ชื่อชนกันเมื่อโปรแกรมใหญ่ขึ้น

ทบทวน Part 17: ใน C เราใช้ `static` ทำให้ฟังก์ชัน/ตัวแปรมองเห็นได้แค่ในไฟล์ `.c` เดียว
(internal linkage) เพื่อป้องกันชื่อชนกันระหว่างไฟล์ต่างๆ ในโปรเจกต์ใหญ่ แต่กลไกนี้มีข้อจำกัด:
ถ้าสองไฟล์ต่างต้อง**เปิดเผย**ฟังก์ชันชื่อเดียวกันออกสู่ภายนอก (ไม่ใช่ `static`) เช่น library A
มีฟังก์ชัน `print()` และ library B ก็มีฟังก์ชัน `print()` เหมือนกัน แต่ทำงานคนละแบบ — ใน C
**ไม่มีทางใช้ทั้งสองฟังก์ชันพร้อมกันในโปรแกรมเดียวได้เลย** เพราะชื่อ `print` ชนกันตรงๆ ที่ระดับ
Linker (ทบทวน Error "multiple definition" จาก Part 17)

C++ แก้ปัญหานี้ด้วย **namespace**: กลไกที่ห่อกลุ่มของชื่อ (ฟังก์ชัน, struct, class, ตัวแปร)
ไว้เป็น "เขต" ของตัวเอง ทำให้ชื่อเดียวกันในคนละ namespace ไม่ชนกันเลย:

```cpp
#include <iostream>
#include <string>

// ห้องสมุด A: จัดการระบบขนส่ง
namespace transport {
    struct Vehicle {
        std::string name;
        int wheels;
    };

    void print(const Vehicle &v) {
        std::cout << "[transport] " << v.name << " มี " << v.wheels << " ล้อ\n";
    }
}

// ห้องสมุด B: จัดการระบบเกม ก็มี struct ชื่อ Vehicle เหมือนกัน แต่ความหมายต่างกันโดยสิ้นเชิง
namespace game {
    struct Vehicle {
        std::string name;
        int speed;
    };

    void print(const Vehicle &v) {
        std::cout << "[game] " << v.name << " ความเร็ว " << v.speed << " km/h\n";
    }
}

int main() {
    transport::Vehicle car{"รถเมล์", 6};
    game::Vehicle race_car{"F1 Car", 350};

    transport::print(car);
    game::print(race_car);

    return 0;
}
```

```
[transport] รถเมล์ มี 6 ล้อ
[game] F1 Car ความเร็ว 350 km/h
```

ทั้ง `transport::Vehicle` และ `game::Vehicle` เป็นคนละชนิดข้อมูลกันโดยสิ้นเชิง แม้ชื่อ
`Vehicle` จะซ้ำกันเป๊ะ — เครื่องหมาย `::` เรียกว่า **Scope Resolution Operator** ทำหน้าที่
"เจาะจง" ว่ากำลังพูดถึงชื่อจาก namespace ไหน

### ทำไมทั้ง C++ Standard Library ถึงอยู่ใน `namespace std`

นี่คือคำตอบว่าทำไมเราต้องเขียน `std::cout`, `std::cin`, `std::string` มาตลอด — **ทุกอย่างใน
C++ Standard Library ถูกห่อไว้ใน `namespace std` ทั้งหมด** เพื่อป้องกันไม่ให้ชื่ออย่าง `cout`,
`string`, `vector`, `max`, `min` (ซึ่งเป็นชื่อที่คนตั้งกันทั่วไปมาก) ไปชนกับชื่อที่โปรแกรมเมอร์
ตั้งเองในโค้ดของตัวเอง Bjarne Stroustrup ออกแบบไว้แบบนี้ตั้งแต่มาตรฐาน C++98 เพื่อให้ทั้ง
Standard Library ของ C++ อยู่ร่วมกับโค้ดของผู้ใช้และไลบรารีอื่นๆ (เช่น Boost) ได้โดยไม่มีทาง
ชื่อชนกันเลย ไม่ว่าโปรเจกต์จะใหญ่แค่ไหนก็ตาม

## 42.6 `using namespace std;` และทำไมไม่ควรใช้ใน Header File (Step 333)

### `using namespace` ช่วยลดความยาวของโค้ด

การเขียน `std::` นำหน้าทุกครั้งอาจดูยาวไปในโปรแกรมเล็กๆ C++ จึงมีคำสั่ง `using namespace`
ที่บอกคอมไพเลอร์ว่า "ให้มองหาชื่อใน namespace นี้โดยไม่ต้องระบุ prefix":

```cpp
#include <iostream>
using namespace std;  // ยอมรับได้ในไฟล์ .cpp เล็กๆ แต่ไม่ควรใช้ใน header (อธิบายด้านล่าง)

int main() {
    string name = "สมชาย";  // ไม่ต้องเขียน std::string อีกต่อไป
    cout << "สวัสดี " << name << endl;
    return 0;
}
```

```
สวัสดี สมชาย
```

### อันตรายที่แท้จริง: ชื่อกำกวม (Ambiguous)

ปัญหาที่แท้จริงของ `using namespace` ไม่ใช่แค่ "ทำให้อ่านยากขึ้นเพราะไม่รู้ว่าชื่อมาจากไหน"
(แม้จะเป็นปัญหาจริง) แต่ปัญหาที่ร้ายแรงกว่าคือ **มันดึงชื่อทั้งหมดจาก namespace นั้นเข้ามาปะปน
กับชื่อในโค้ดของเรา** ถ้าเผลอตั้งชื่อซ้ำกับ namespace อื่นที่ถูก `using` ไว้เหมือนกัน จะเกิด
ปัญหาชื่อกำกวมทันที ลองดูตัวอย่างที่ใช้ namespace ของเราเองสองอันจากหัวข้อ 42.5:

```cpp
#include <iostream>
#include <string>

namespace transport {
    struct Vehicle {
        std::string name;
        int wheels;
    };
}

namespace game {
    struct Vehicle {
        std::string name;
        int speed;
    };
}

using namespace transport;
using namespace game;

int main() {
    Vehicle v{"test", 4};  // ผิด: Vehicle กำกวม เพราะมีทั้งใน transport และ game
    std::cout << v.name << '\n';
    return 0;
}
```

```
error: reference to 'Vehicle' is ambiguous
note: candidates are: 'struct game::Vehicle'
note:                 'struct transport::Vehicle'
error: 'v' was not declared in this scope
```

นี่คือเหตุผลที่แท้จริงว่าทำไม `using namespace std;` ถึงเสี่ยง: `namespace std` มีชื่อ**หลาย
พันชื่อ** (`count`, `distance`, `find`, `sort`, `list`, `move`, `data`, ...) ถ้าโปรเจกต์ของเรา
เผลอตั้งชื่อฟังก์ชันหรือตัวแปรซ้ำกับชื่อเหล่านี้ (ซึ่งเกิดขึ้นได้ง่ายมากเพราะเป็นชื่อสามัญที่คน
ใช้กันทั่วไป) แล้วบังเอิญ include header ตัวใหม่ที่ทำให้ชื่อนั้นถูกดึงเข้ามาพอดี โปรแกรมที่เคย
คอมไพล์ผ่านอาจจะ**พังทันทีโดยไม่มีการเตือนล่วงหน้าเลย**

### กฎทอง: ห้ามเขียน `using namespace` ใน Header File เด็ดขาด

```cpp
// my_utils.h — ตัวอย่างที่ผิด ห้ามทำแบบนี้!
#ifndef MY_UTILS_H
#define MY_UTILS_H

using namespace std;  // อันตรายมาก!

// ...
#endif
```

เหตุผลร้ายแรงกว่าการเขียนใน `.cpp` มาก: **ทุกไฟล์ที่ `#include "my_utils.h"` จะถูกบังคับให้รับ
`using namespace std;` ไปด้วยโดยอัตโนมัติ** ไม่ว่าไฟล์นั้นจะต้องการหรือไม่ก็ตาม (ทบทวนกลไกของ
`#include` จาก Part 14: มันแค่ก็อปเนื้อหาทั้งหมดของ header เข้าไปแปะในไฟล์ที่ include) ยิ่ง
โปรเจกต์มีไฟล์ header เชื่อมโยงกันซับซ้อนมากเท่าไร (ทบทวน Dependency Graph จาก Part 17)
โอกาสเกิดชื่อชนกันก็ยิ่งสูงขึ้นเท่านั้น และที่แย่ที่สุดคือ **ผู้ที่ได้รับผลกระทบคือไฟล์อื่นที่ไม่
รู้อิโหน่อิเหน่เลยว่ามี `using namespace std;` ซ่อนอยู่ในไฟล์ที่ตัวเอง include มา**

> **แนวทางปฏิบัติที่ถูกต้องของหลักสูตรนี้**:
> 1. **ห้ามเขียน `using namespace` ใน header file (`.h`/`.hpp`) เด็ดขาด**
> 2. ในไฟล์ `.cpp` เขียนได้ แต่ควรจำกัดให้แคบที่สุดเท่าที่จะทำได้ เช่น `using std::cout;`
>    (ดึงมาแค่ชื่อเดียว ไม่ใช่ทั้ง namespace) หรือจำกัดขอบเขตไว้แค่ในฟังก์ชันเดียวแทนที่จะ
>    เขียนไว้ที่ระดับบนสุดของไฟล์
> 3. ในโปรเจกต์ขนาดใหญ่ระดับมืออาชีพ (ทบทวนจะเจอใน Part 80 — C++ Core Guidelines) มักจะ
>    เขียน `std::` เต็มๆ ทุกครั้งไปเลย เพื่อความชัดเจนสูงสุดว่าแต่ละชื่อมาจากไหน แม้จะดูยาว
>    กว่าเล็กน้อยก็ตาม — หลักสูตรนี้จะใช้แนวทางเขียน `std::` เต็มในตัวอย่างโค้ดส่วนใหญ่นับจาก
>    นี้ไป เพื่อฝึกให้เห็นชัดเจนว่าแต่ละชื่อมาจาก Standard Library จริงๆ

## 42.7 สร้าง Namespace ของตัวเอง (Step 334)

เมื่อโปรเจกต์ใหญ่ขึ้น (จะเห็นชัดเจนตอนทำโปรเจกต์ปิดท้าย Module D ใน Part 55) การจัดกลุ่มฟังก์ชัน
และ struct/class ที่เกี่ยวข้องกันไว้ใน namespace ของตัวเองช่วยให้โค้ดเป็นระเบียบและป้องกันชื่อ
ชนกับไลบรารีอื่นได้ตั้งแต่ต้น:

```cpp
#include <iostream>

namespace mathutil {
    const double PI = 3.14159265358979;

    double circle_area(double radius) {
        return PI * radius * radius;
    }

    double circle_circumference(double radius) {
        return 2 * PI * radius;
    }

    // namespace ซ้อนใน namespace ได้ (nested namespace)
    namespace advanced {
        double sphere_volume(double radius) {
            return (4.0 / 3.0) * PI * radius * radius * radius;
        }
    }
}

int main() {
    double r = 2.0;
    std::cout << "พื้นที่วงกลม r=" << r << " คือ " << mathutil::circle_area(r) << '\n';
    std::cout << "เส้นรอบวง r=" << r << " คือ " << mathutil::circle_circumference(r) << '\n';
    std::cout << "ปริมาตรทรงกลม r=" << r << " คือ "
               << mathutil::advanced::sphere_volume(r) << '\n';

    // ใช้ using เพื่อลดความยาวเฉพาะบางส่วน (ทางเลือกระหว่าง using ทั้ง namespace กับ :: เสมอ)
    using mathutil::circle_area;
    std::cout << "เรียกซ้ำแบบสั้น: " << circle_area(r) << '\n';

    return 0;
}
```

```
พื้นที่วงกลม r=2 คือ 12.5664
เส้นรอบวง r=2 คือ 12.5664
ปริมาตรทรงกลม r=2 คือ 33.5103
เรียกซ้ำแบบสั้น: 12.5664
```

### จุดที่ควรสังเกต

- **`namespace mathutil { ... }` ไม่มี `;` ปิดท้าย** ต่างจากการปิด struct/class ที่ต้องมี `;`
  เสมอ (ทบทวนจาก Part 10) — เป็นจุดที่มือใหม่มักพลาดตอนเริ่มเขียน C++
- **Nested namespace** (`mathutil::advanced`) ใช้จัดกลุ่มย่อยลงไปอีกชั้นได้ตามต้องการ เข้าถึง
  ด้วยการต่อ `::` ไปเรื่อยๆ (`mathutil::advanced::sphere_volume`) ตั้งแต่ C++17 เป็นต้นไป
  สามารถเขียนแบบย่อได้เป็น `namespace mathutil::advanced { ... }` ในคำประกาศเดียว แทนที่จะ
  ต้องซ้อนวงเล็บปีกกาสองชั้นแบบในตัวอย่าง
- **`using mathutil::circle_area;`** คือการดึงมาแค่**ชื่อเดียว** (ไม่ใช่ทั้ง namespace) เป็น
  แนวทางที่ปลอดภัยกว่า `using namespace mathutil;` มาก เพราะจำกัดความเสี่ยงเรื่องชื่อชนกันไว้
  แค่ชื่อเดียวที่เราตั้งใจดึงมาจริงๆ — ทบทวนหลักการเดียวกับที่แนะนำไว้ในหัวข้อ 42.6

## 42.8 `std::string` เบื้องต้น (Step 335)

ทบทวน Part 7: ใน C string คือ array ของ `char` ที่จบด้วย `'\0'` ต้องจัดการหน่วยความจำเองทั้งหมด
ผ่านฟังก์ชันใน `<string.h>` เช่น `strlen`, `strcpy`, `strcat` — และถ้าจัดการผิดพลาด (เช่น
`strcpy` overflow buffer) จะเกิด Buffer Overflow ทันที (ทบทวนอันตรายนี้จาก Part 38)

C++ มี `std::string` (จาก `<string>`) เป็นชนิดข้อมูลที่**จัดการหน่วยความจำให้อัตโนมัติ**
ทั้งหมด ขยายขนาดเองเมื่อจำเป็น ไม่มีปัญหา Buffer Overflow จากการต่อ string อีกต่อไป — Part นี้
จะแนะนำแค่การใช้งานพื้นฐานที่จำเป็น ส่วนรายละเอียดเชิงลึก (เช่น `string_view`, การจัดการ
หน่วยความจำภายใน, Regular Expression) จะเจาะลึกเต็มรูปแบบใน **Part 65**

```cpp
#include <iostream>
#include <string>

int main() {
    std::string first_name = "Somchai";
    std::string last_name = "Jaidee";

    std::string full_name = first_name + " " + last_name;  // + คือ concatenation
    std::cout << "ชื่อเต็ม: " << full_name << '\n';
    std::cout << "ความยาว: " << full_name.length() << " ตัวอักษร\n";
    std::cout << "ตัวอักษรแรก: " << full_name[0] << '\n';

    full_name += "!";  // ต่อท้ายด้วย +=
    std::cout << "หลังต่อท้าย: " << full_name << '\n';

    if (full_name.find("Jaidee") != std::string::npos) {
        std::cout << "พบคำว่า Jaidee ในชื่อเต็ม\n";
    }

    std::string city;
    std::cout << "กรอกชื่อเมือง: ";
    std::getline(std::cin, city);  // อ่านทั้งบรรทัดรวมช่องว่าง (ต่างจาก >> ที่หยุดที่ช่องว่าง)
    std::cout << "เมืองของคุณคือ: " << city << '\n';

    return 0;
}
```

ตัวอย่างการรัน (ป้อน `Bangkok` ตอน prompt "กรอกชื่อเมือง"):

```
ชื่อเต็ม: Somchai Jaidee
ความยาว: 14 ตัวอักษร
ตัวอักษรแรก: S
หลังต่อท้าย: Somchai Jaidee!
พบคำว่า Jaidee ในชื่อเต็ม
กรอกชื่อเมือง: เมืองของคุณคือ: Bangkok
```

### สรุปเมธอดพื้นฐานที่ใช้บ่อยที่สุดของ `std::string`

| เมธอด/ตัวดำเนินการ | ความหมาย | เทียบเท่าใน C (`<string.h>`) |
|---|---|---|
| `s1 + s2` | ต่อ string สอง (concatenation) คืนตัวใหม่ | `strcat` (ต้องจัดการ buffer เอง) |
| `s += s2` | ต่อท้ายเข้ากับตัวเดิม | `strcat(s, s2)` |
| `s.length()` หรือ `s.size()` | จำนวนตัวอักษร (ทั้งคู่ทำงานเหมือนกันทุกประการ) | `strlen(s)` |
| `s[i]` | เข้าถึงตัวอักษรที่ตำแหน่ง `i` | `s[i]` (เหมือนกัน เพราะยังเป็น array ภายใน) |
| `s.find(sub)` | หาตำแหน่งของ substring คืน `std::string::npos` ถ้าไม่พบ | `strstr` (คืน pointer หรือ `NULL`) |
| `s.empty()` | ตรวจว่า string ว่างเปล่าหรือไม่ | `strlen(s) == 0` |
| `std::getline(std::cin, s)` | อ่านทั้งบรรทัดรวมช่องว่าง | `fgets` (ต้องกำหนดขนาด buffer เอง) |

### ทำไมต้องรู้จัก `std::string::npos`

`std::string::npos` คือค่าคงที่พิเศษ (มีค่าเท่ากับค่าสูงสุดของ `size_t`) ที่ `.find()` คืนกลับมา
เมื่อ**ไม่พบ**สิ่งที่ค้นหาเลย เทียบเท่ากับการที่ `strstr()` ของ C คืน `NULL` เมื่อไม่พบ — ต้อง
เปรียบเทียบด้วย `!= std::string::npos` เสมอ (ไม่ใช่เปรียบเทียบกับ `-1` หรือ `0` ตรงๆ) เพราะ
`npos` เป็นค่าคงที่พิเศษของคลาส `std::string` โดยเฉพาะ

> **สำคัญ**: `std::cin >> s` เมื่อ `s` เป็น `std::string` จะ**หยุดอ่านที่ whitespace ตัวแรก**
> (เหมือน `%s` ของ `scanf`) ถ้าต้องการอ่านทั้งบรรทัดรวมช่องว่าง (เช่นชื่อเมืองที่มีสองคำอย่าง
> "New York") **ต้องใช้ `std::getline(std::cin, s)` เท่านั้น** นี่คือ Common Pitfall ที่พบบ่อย
> มากสำหรับผู้เริ่มเขียน C++ — จะสรุปไว้อีกครั้งในหัวข้อท้ายบท

## 42.9 `std::endl` เทียบกับ `"\n"` (Step 336)

ตลอด Part นี้เราใช้ทั้ง `std::endl` และ `'\n'` ปะปนกันไปโดยตั้งใจ ถึงเวลาอธิบายความแตกต่างที่
แท้จริงระหว่างสองแบบนี้

### `'\n'` คือแค่อักขระขึ้นบรรทัดใหม่

`'\n'` เป็นแค่ **อักขระ** (character) ตัวหนึ่งเหมือนที่เรียนมาตั้งแต่ Part 1 — เมื่อส่งเข้าไป
ใน stream มันจะถูกเก็บไว้ใน **buffer ภายใน** ของ stream ก่อน ยังไม่ถูกส่งออกไปยังหน้าจอ/ไฟล์
จริงทันที (buffer จะถูกส่งออกจริงเมื่อเต็ม หรือเมื่อโปรแกรมจบ หรือเมื่อถูกสั่ง flush อย่างชัดเจน)

### `std::endl` คือ `'\n'` บวกกับการ Flush Buffer ทันที

`std::endl` ทำสองอย่างพร้อมกัน: (1) ขึ้นบรรทัดใหม่เหมือน `'\n'` และ (2) **บังคับให้ stream
ส่งข้อมูลทั้งหมดที่ค้างอยู่ใน buffer ออกไปทันที** (เรียกว่า **flush**) การ flush ทุกครั้งมี
ค่าใช้จ่ายด้าน performance ที่มากกว่าการปล่อยให้ buffer จัดการเองตามธรรมชาติพอสมควร โดยเฉพาะ
เมื่อพิมพ์ข้อมูลจำนวนมากในลูป

```cpp
#include <chrono>
#include <iostream>

int main() {
    const int n = 100000;

    auto start1 = std::chrono::steady_clock::now();
    for (int i = 0; i < n; i++) {
        std::cout << i << "\n";
    }
    auto end1 = std::chrono::steady_clock::now();

    auto start2 = std::chrono::steady_clock::now();
    for (int i = 0; i < n; i++) {
        std::cout << i << std::endl;
    }
    auto end2 = std::chrono::steady_clock::now();

    auto ms1 = std::chrono::duration_cast<std::chrono::milliseconds>(end1 - start1).count();
    auto ms2 = std::chrono::duration_cast<std::chrono::milliseconds>(end2 - start2).count();

    std::cerr << "\\n ใช้เวลา: " << ms1 << " ms\n";
    std::cerr << "std::endl ใช้เวลา: " << ms2 << " ms\n";

    return 0;
}
```

ตัวอย่างผลลัพธ์ (ตัวเลขจริงจะต่างกันไปตามเครื่องแต่ละเครื่อง แนวโน้มจะเป็นแบบนี้เสมอ):

```
\n ใช้เวลา: 7 ms
std::endl ใช้เวลา: 22 ms
```

`std::endl` ช้ากว่าเห็นได้ชัดในตัวอย่างนี้ (ราว 3 เท่า) เพราะสั่ง flush buffer ทุกครั้งที่พิมพ์
100,000 ครั้ง ในขณะที่ `"\n"` ปล่อยให้ระบบ buffer จัดการการส่งออกอย่างมีประสิทธิภาพเอง (ทบทวน
แนวคิดเรื่อง Buffered I/O จาก Part 3)

> **แนวทางปฏิบัติที่ดีของหลักสูตรนี้**: ใช้ `'\n'` เป็นค่าเริ่มต้นเสมอสำหรับการขึ้นบรรทัดใหม่
> ทั่วไป และใช้ `std::endl` เฉพาะเมื่อ**ต้องการบังคับ flush จริงๆ** เช่น ก่อนที่โปรแกรมจะ crash
> หรือหยุดทำงานกะทันหัน (ต้องการให้ log ที่พิมพ์ไปแล้วปรากฏแน่นอนก่อนโปรแกรมตาย) หรือเมื่อพิมพ์
> ข้อความ prompt ที่รอ input ทันที (เช่น `"ป้อนตัวเลข: "` ที่ต้องการให้ผู้ใช้เห็นทันทีก่อนเริ่ม
> รอ `std::cin`) สำหรับ `std::cout` โดยทั่วไป stream จะ flush อัตโนมัติเมื่อโปรแกรมจบอยู่แล้ว
> จึงไม่ต้องกังวลว่าข้อความจะหายไปถ้าใช้ `'\n'` เป็นหลัก

## ข้อผิดพลาดที่พบบ่อย (Common Pitfalls)

1. **ใช้ `std::cin >> s` กับ `std::string` ที่ต้องการรับข้อความมีช่องว่าง** — `>>` จะหยุดอ่าน
   ที่ whitespace ตัวแรกเสมอ (เหมือน `%s` ของ `scanf`) ถ้าต้องการทั้งบรรทัดต้องใช้
   `std::getline(std::cin, s)` เท่านั้น
2. **ลืม `.clear()` และ `.ignore()` เมื่อ `std::cin` เข้าสู่ fail state** — ทำให้โปรแกรมค้าง
   เป็น infinite loop หรือได้ค่าผิดพลาดต่อเนื่องไปเรื่อยๆ ทั้งสองเมธอดต้องเรียกคู่กันเสมอ
   (ทบทวนหัวข้อ 42.3)
3. **ผสม `std::cin >> x` กับ `std::getline()` ในโปรแกรมเดียวกันโดยไม่ระวัง** — หลังจาก
   `std::cin >> x` อ่านตัวเลข อักขระ `'\n'` ที่ผู้ใช้กด Enter จะยังค้างอยู่ใน buffer เมื่อเรียก
   `std::getline()` ต่อทันที มันจะอ่านได้ string ว่างเปล่าทันที (เพราะเจอ `'\n'` ที่ค้างอยู่
   ก่อน) วิธีแก้คือเรียก `std::cin.ignore()` คั่นกลางก่อนเรียก `std::getline()`
4. **เขียน `using namespace std;` ใน header file** — ทำให้ทุกไฟล์ที่ `#include` header นั้น
   ถูกบังคับรับผลกระทบไปด้วยโดยไม่รู้ตัว เพิ่มความเสี่ยงเรื่องชื่อชนกันในระดับที่ควบคุมไม่ได้
   (ทบทวนหัวข้อ 42.6)
5. **ลืม `;` ปิดท้าย namespace หรือใส่เกินมา** — `namespace X { ... }` **ไม่ต้องมี** `;` ปิด
   ท้าย ต่างจาก `struct`/`class`/`enum` ที่ต้องมี เป็นจุดสับสนที่พบบ่อยตอนเริ่มเขียน C++
6. **เข้าใจผิดว่า `std::endl` กับ `"\n"` เหมือนกันทุกประการ** — ทั้งคู่ขึ้นบรรทัดใหม่เหมือนกัน
   แต่ `std::endl` มี overhead จากการ flush buffer เพิ่มเข้ามาเสมอ ควรเลือกใช้ `"\n"` เป็นค่า
   เริ่มต้นในโค้ดที่พิมพ์ข้อมูลจำนวนมาก

## แบบฝึกหัดท้ายบท

1. เขียนโปรแกรม `bmi_calculator.cpp` ที่รับน้ำหนัก (กก.) และส่วนสูง (เมตร) จากผู้ใช้ด้วย
   `std::cin` คำนวณค่า BMI แล้วพิมพ์ผลลัพธ์ด้วย `std::cout` ต้องมีการตรวจสอบ fail state ของ
   `std::cin` ด้วย (ถ้าผู้ใช้พิมพ์ตัวอักษรแทนตัวเลขต้องแจ้งเตือนและให้กรอกใหม่)
2. เขียนโปรแกรมที่มี namespace ของตัวเองชื่อ `stringutil` ที่มีฟังก์ชัน `to_upper` (แปลง
   ตัวอักษรภาษาอังกฤษเป็นตัวพิมพ์ใหญ่ทั้งหมด) และ `count_vowels` (นับจำนวนสระภาษาอังกฤษ
   a, e, i, o, u ใน string) โดยใช้ `std::string` ตลอดทั้งโปรแกรม
3. เขียนโปรแกรมที่รับชื่อเต็ม (มีช่องว่าง เช่น "สมชาย ใจดี") ด้วย `std::getline` แล้วรับอายุ
   ด้วย `std::cin >> age` ต่อจากกัน สาธิตปัญหา `'\n'` ค้างใน buffer ที่อธิบายใน Common Pitfall
   ข้อ 3 แล้วแก้ไขให้ทำงานถูกต้อง
4. เขียนโปรแกรมที่สร้างสอง namespace ชื่อ `zoo` และ `office` ที่ต่างก็มี struct ชื่อ `Cage`
   (หรือชื่ออื่นที่ซ้ำกัน) แล้วทดลองใช้ `using namespace` ทั้งคู่พร้อมกัน สังเกต Error ที่เกิด
   ขึ้น แล้วแก้ไขด้วยการระบุ `::` แทน
5. เขียนโปรแกรมค้นหาว่าคำว่า `"error"` อยู่ใน log message ที่กำหนดหรือไม่ โดยใช้
   `std::string::find` และ `std::string::npos` ให้ถูกต้อง
6. ทดลองเขียนโปรแกรมที่พิมพ์ตัวเลข 1 ถึง 50,000 ด้วย `std::endl` เทียบกับ `'\n'` วัดเวลาด้วย
   `<chrono>` เหมือนหัวข้อ 42.9 แล้วอธิบายผลลัพธ์ที่ได้ด้วยคำพูดของตัวเอง

### แนวทางเฉลยข้อ 2

```cpp
#include <cctype>
#include <iostream>
#include <string>

namespace stringutil {
    std::string to_upper(const std::string &s) {
        std::string result = s;
        for (char &c : result) {
            c = static_cast<char>(std::toupper(static_cast<unsigned char>(c)));
        }
        return result;
    }

    int count_vowels(const std::string &s) {
        int count = 0;
        for (char c : s) {
            char lower = static_cast<char>(std::tolower(static_cast<unsigned char>(c)));
            if (lower == 'a' || lower == 'e' || lower == 'i' || lower == 'o' || lower == 'u') {
                count++;
            }
        }
        return count;
    }
}

int main() {
    std::string text = "Hello World from Cpp";

    std::cout << "ต้นฉบับ: " << text << '\n';
    std::cout << "ตัวพิมพ์ใหญ่: " << stringutil::to_upper(text) << '\n';
    std::cout << "จำนวนสระ: " << stringutil::count_vowels(text) << '\n';

    return 0;
}
```

```bash
g++ -Wall -Wextra -Wpedantic -std=c++17 vowel_util.cpp -o vowel_util
./vowel_util
```

```
ต้นฉบับ: Hello World from Cpp
ตัวพิมพ์ใหญ่: HELLO WORLD FROM CPP
จำนวนสระ: 4
```

จุดสำคัญของเฉลยนี้: ทั้งสองฟังก์ชันถูกห่อไว้ใน `namespace stringutil` ตามที่โจทย์ขอ เรียกใช้
ผ่าน `stringutil::to_upper(...)` และ `stringutil::count_vowels(...)` อย่างชัดเจน (ไม่ใช้
`using namespace`) สังเกตการ cast `static_cast<unsigned char>(c)` ก่อนส่งเข้า `std::toupper`/
`std::tolower` เพราะฟังก์ชันทั้งสองรับ `int` และมีพฤติกรรมไม่นิยาม (Undefined Behavior) ถ้า
ส่ง `char` ที่เป็นค่าลบเข้าไปตรงๆ บนระบบที่ `char` เป็น signed โดยค่าเริ่มต้น (ทบทวนความรู้เรื่อง
signedness ของ `char` จาก Part 2)

### แนวทางเฉลยข้อ 3

```cpp
#include <iostream>
#include <string>

int main() {
    std::string full_name;
    int age = 0;

    std::cout << "กรอกชื่อเต็ม: ";
    std::getline(std::cin, full_name);

    std::cout << "กรอกอายุ: ";
    std::cin >> age;
    std::cin.ignore();  // ทิ้ง '\n' ที่ค้างอยู่หลัง cin >> age เพื่อไม่ให้ getline ครั้งถัดไปพัง

    std::string hobby;
    std::cout << "กรอกงานอดิเรก: ";
    std::getline(std::cin, hobby);

    std::cout << "\n=== สรุปข้อมูล ===\n";
    std::cout << "ชื่อ: " << full_name << '\n';
    std::cout << "อายุ: " << age << " ปี\n";
    std::cout << "งานอดิเรก: " << hobby << '\n';

    return 0;
}
```

ทดสอบด้วยการป้อน `"สมชาย ใจดี"`, `25`, `"อ่านหนังสือ"` ตามลำดับ:

```
กรอกชื่อเต็ม: สมชาย ใจดี
กรอกอายุ: 25
กรอกงานอดิเรก: อ่านหนังสือ

=== สรุปข้อมูล ===
ชื่อ: สมชาย ใจดี
อายุ: 25 ปี
งานอดิเรก: อ่านหนังสือ
```

จุดสำคัญที่สุดของเฉลยนี้คือบรรทัด `std::cin.ignore();` ทันทีหลัง `std::cin >> age` — ถ้าไม่มี
บรรทัดนี้ `std::getline(std::cin, hobby)` ตัวถัดไปจะอ่านได้ string ว่างเปล่าทันที เพราะไปเจอ
อักขระ `'\n'` ที่ผู้ใช้กด Enter หลังพิมพ์ `25` ซึ่งยังค้างอยู่ใน buffer ของ `std::cin` (ค่า
เริ่มต้นของ `.ignore()` เมื่อไม่ระบุ argument คือทิ้งไปแค่ 1 ตัวอักษร ซึ่งเพียงพอสำหรับกรณีนี้
ที่รู้แน่ชัดว่ามี `'\n'` ค้างอยู่แค่ตัวเดียว)

## สรุปท้ายบท

ใน Part นี้เราได้:

- เข้าใจแนวคิดเรื่อง Stream ของ C++ และทำไม `std::cout`/`std::cin` ถึงปลอดภัยกว่า
  `printf`/`scanf` ในแง่การตรวจสอบชนิดข้อมูล เพราะไม่ต้องพึ่ง format specifier ที่จับคู่ผิดได้
  อีกต่อไป
- ใช้ stream insertion (`<<`) และ extraction (`>>`) operator ได้อย่างคล่องแคล่ว รวมถึงจัดการ
  fail state ของ `std::cin` ด้วย `.clear()` และ `.ignore()` เมื่อผู้ใช้ป้อนข้อมูลผิดชนิด
- เข้าใจว่า **namespace** แก้ปัญหาชื่อชนกันในโปรแกรมขนาดใหญ่ได้อย่างไร และทำไมทั้ง C++
  Standard Library ถึงอยู่ใน `namespace std`
- เข้าใจอันตรายที่แท้จริงของ `using namespace std;` (ปัญหาชื่อกำกวมที่อาจเกิดขึ้นแบบไม่คาดคิด)
  และกฎทองที่ต้องยึดถือ: **ห้ามเขียนไว้ใน header file เด็ดขาด**
- สร้าง namespace ของตัวเองพร้อม nested namespace เพื่อจัดระเบียบโค้ดในโปรเจกต์ขนาดใหญ่
- ใช้ `std::string` เบื้องต้นได้ครบทั้งการต่อ string, หาความยาว, ค้นหาข้อความ, และอ่านทั้ง
  บรรทัดด้วย `std::getline`
- เข้าใจความแตกต่างระหว่าง `std::endl` (ขึ้นบรรทัดใหม่ + flush buffer) กับ `"\n"` (ขึ้นบรรทัด
  ใหม่เฉยๆ) และรู้ว่าควรเลือกใช้แบบไหนในสถานการณ์ใด

ใน **Part 43** เราจะเจาะลึกเรื่อง **Reference และ const** ซึ่งเป็นรากฐานสำคัญที่สุดอย่างหนึ่ง
ของ C++ ที่ปูทางไปสู่การเขียนฟังก์ชันอย่างปลอดภัยและมีประสิทธิภาพ — จะได้เห็นคำตอบเต็มรูปแบบว่า
ทำไม `std::cin >> a` ไม่ต้องใช้ `&` เหมือน `scanf` ตามที่ค้างไว้ในหัวข้อ 42.2
