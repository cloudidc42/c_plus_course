## 25.1 ทบทวน Recursion และแนวคิด Recursion Tree (Step 193)

ใน **Part 6** เราได้เรียนรู้ Recursion เบื้องต้นไปแล้ว: ฟังก์ชันที่เรียกตัวเองซ้ำๆ โดยต้อง
มี **Base Case** (เงื่อนไขหยุด) และ **Recursive Case** (เงื่อนไขที่เรียกตัวเองต่อด้วยปัญหา
ที่เล็กลง) ตัวอย่างคลาสสิกที่สุดคือ Factorial:

```c
long factorial(int n) {
    if (n <= 1) {
        return 1;             /* Base Case */
    }
    return n * factorial(n - 1); /* Recursive Case */
}
```

Factorial มีลักษณะพิเศษคือเรียกตัวเอง **แค่ 1 ครั้ง** ในแต่ละระดับ (Linear Recursion) ทำให้
เมื่อวาดเป็น "สายโซ่การเรียก" จะได้เส้นตรงเส้นเดียว: `factorial(5) -> factorial(4) ->
factorial(3) -> factorial(2) -> factorial(1)` ความซับซ้อนจึงเป็น O(n) ตรงไปตรงมา

แต่ใน Part นี้เราจะพบกับ Recursion อีกแบบที่เรียกตัวเอง **มากกว่า 1 ครั้ง** ในแต่ละระดับ
(Tree Recursion) ซึ่งเมื่อวาดออกมาจะได้ภาพเป็น **ต้นไม้ (Tree)** ไม่ใช่เส้นตรง — และนี่คือ
จุดเริ่มต้นของปัญหาที่ Dynamic Programming เข้ามาช่วยแก้ไข

### Recursion Tree คืออะไร

**Recursion Tree** คือแผนภาพที่แสดงลำดับการเรียกฟังก์ชันแบบ Recursive ทั้งหมด โดยแต่ละ
"กิ่ง" แทนการเรียกฟังก์ชันครั้งหนึ่ง และ "ลูก" ของแต่ละ node คือการเรียกซ้ำที่เกิดขึ้นภายใน
ฟังก์ชันนั้น การวาด Recursion Tree ช่วยให้เรา:

1. **มองเห็นภาพรวม**ของลำดับการทำงานทั้งหมด แทนที่จะจินตนาการในหัวเฉยๆ
2. **นับจำนวนการเรียกฟังก์ชันทั้งหมด** ได้อย่างเป็นระบบ (นับจำนวน node ในต้นไม้)
3. **สังเกตเห็น "งานที่ทำซ้ำโดยไม่จำเป็น"** ได้ง่ายขึ้นมาก ซึ่งเป็นกุญแจสำคัญที่นำไปสู่แนวคิด
   Dynamic Programming

ในหัวข้อถัดไป เราจะใช้ตัวอย่าง **Fibonacci Sequence** ซึ่งเป็นตัวอย่างที่ดีที่สุดในการแสดง
Recursion Tree แบบ Tree Recursion เพราะเรียกตัวเอง **2 ครั้ง** ในทุกระดับ

## 25.2 Naive Fibonacci และ Exponential Blowup (Step 194)

ลำดับ **Fibonacci** คือลำดับตัวเลขที่แต่ละตัวเป็นผลรวมของสองตัวก่อนหน้า โดยเริ่มจาก
`fib(0) = 0` และ `fib(1) = 1`:

```
fib(0)=0, fib(1)=1, fib(2)=1, fib(3)=2, fib(4)=3, fib(5)=5, fib(6)=8, fib(7)=13, ...
```

นิยามทางคณิตศาสตร์: `fib(n) = fib(n-1) + fib(n-2)` เมื่อ `n >= 2` — นิยามนี้แปลงเป็นโค้ด
Recursive ได้ตรงตัวทันที:

```c
long fib_naive(int n) {
    if (n <= 1) {
        return n;
    }
    return fib_naive(n - 1) + fib_naive(n - 2);
}
```

### วัดจำนวนครั้งที่ฟังก์ชันถูกเรียกจริง

```c
/* ============================================================
 * ชื่อไฟล์:     fib_naive.c
 * คำอธิบาย:     Naive Recursive Fibonacci พร้อมนับจำนวนครั้งที่เรียกฟังก์ชันจริง
 * ============================================================ */
#include <stdio.h>

long fib_naive(int n);
long call_count = 0;

int main(void) {
    for (int i = 0; i <= 10; i++) {
        call_count = 0;
        long result = fib_naive(i);
        printf("fib(%2d) = %-4ld  (จำนวนครั้งที่เรียกฟังก์ชัน = %ld)\n",
               i, result, call_count);
    }
    return 0;
}

long fib_naive(int n) {
    call_count++;
    if (n <= 1) {
        return n;
    }
    return fib_naive(n - 1) + fib_naive(n - 2);
}
```

```bash
gcc -Wall -Wextra -Wpedantic -std=c17 fib_naive.c -o fib_naive
./fib_naive
```

```
fib( 1) = 1     (จำนวนครั้งที่เรียกฟังก์ชัน = 1)
fib( 2) = 1     (จำนวนครั้งที่เรียกฟังก์ชัน = 3)
fib( 3) = 2     (จำนวนครั้งที่เรียกฟังก์ชัน = 5)
fib( 4) = 3     (จำนวนครั้งที่เรียกฟังก์ชัน = 9)
fib( 5) = 5     (จำนวนครั้งที่เรียกฟังก์ชัน = 15)
fib( 6) = 8     (จำนวนครั้งที่เรียกฟังก์ชัน = 25)
fib( 7) = 13    (จำนวนครั้งที่เรียกฟังก์ชัน = 41)
fib( 8) = 21    (จำนวนครั้งที่เรียกฟังก์ชัน = 67)

```

### วาด Recursion Tree ของ fib(5)

```
                              fib(5)
                          /            \
                     fib(4)              fib(3)
                    /      \             /      \
               fib(3)      fib(2)    fib(2)      fib(1)
               /    \      /    \    /    \
          fib(2)  fib(1) fib(1) fib(0) fib(1) fib(0)
          /    \
       fib(1) fib(0)
```

สังเกตสิ่งที่สำคัญที่สุดในภาพนี้: **`fib(3)` ถูกคำนวณซ้ำ 2 ครั้ง**, **`fib(2)` ถูกคำนวณซ้ำ
ถึง 3 ครั้ง**, **`fib(1)` และ `fib(0)` ถูกคำนวณซ้ำหลายครั้งมาก — นี่คือปรากฏการณ์ที่เรียกว่า
**Overlapping Subproblems (ปัญหาย่อยที่ซ้อนทับกัน)** ซึ่งเป็นต้นเหตุของความสิ้นเปลืองมหาศาล

### ทำไมถึงเรียกว่า "ระเบิด (Blowup)"

จำนวนการเรียกฟังก์ชันทั้งหมดของ `fib_naive(n)` เติบโตในอัตรา **O(2ⁿ)** (แม่นยำกว่าคือ
O(φⁿ) โดย φ ≈ 1.618 แต่ในทางปฏิบัติมักประมาณเป็น O(2ⁿ) เพราะยังคงเป็น Exponential เหมือนกัน)
มาดูตัวเลขจริงเพื่อให้เห็นภาพว่า "ระเบิด" ขนาดไหน:

| n | จำนวนครั้งที่เรียกฟังก์ชัน (ประมาณ) | เวลาโดยประมาณ (สมมติ CPU เร็ว 10⁹ ครั้ง/วินาที) |
|---|---|---|
| 10 | 177 | เร็วมาก แทบไม่รู้สึก |
| 20 | 21,891 | เร็วมาก แทบไม่รู้สึก |
| 30 | ~2.7 ล้าน | เสี้ยววินาที |
| 40 | ~331 ล้าน | ประมาณ 0.3 วินาที |
| 50 | ~40,000 ล้าน | ประมาณ 40 วินาที |
| 60 | ~5 ล้านล้าน | ประมาณ 1 ชั่วโมงครึ่ง |
| 100 | ~10²¹ | นานกว่าอายุจักรวาล! |

จากตารางนี้จะเห็นว่าแค่เพิ่ม `n` จาก 40 เป็น 50 (เพิ่มขึ้นแค่ 10) เวลาทำงานเพิ่มขึ้นจาก
0.3 วินาทีเป็น 40 วินาที — นี่คือธรรมชาติของ Exponential Growth ที่ "ดูเหมือนโอเค" ตอนอินพุต
เล็ก แต่ **ใช้งานจริงไม่ได้เลย** เมื่ออินพุตโตขึ้นแม้เพียงเล็กน้อย

**คำถามสำคัญ**: ทั้งที่ค่า `fib(0)` ถึง `fib(n)` มีแค่ `n+1` ค่าที่ไม่ซ้ำกันเลย ทำไมเราถึง
ต้องคำนวณมันซ้ำแล้วซ้ำเล่านับล้านครั้ง? นี่คือคำถามที่ Dynamic Programming ตอบได้อย่างสวยงาม

## 25.3 Memoization: Top-down Dynamic Programming (Step 195)

**แนวคิด**: ทุกครั้งที่คำนวณค่า `fib(k)` เสร็จแล้ว ให้ **จดจำ (memoize)** ค่านั้นไว้ในตาราง
(เช่นอาร์เรย์) ก่อน ครั้งต่อไปที่ต้องการ `fib(k)` อีก ให้ **ตรวจสอบตารางก่อน** ถ้ามีอยู่แล้ว
ก็คืนค่าจากตารางทันทีโดยไม่ต้องคำนวณซ้ำเลย

เทคนิคนี้เรียกว่า **Top-down Dynamic Programming** เพราะยังคงเขียนโค้ดในรูปแบบ Recursive
เหมือนเดิม (เริ่มจากปัญหาใหญ่ `fib(n)` แล้วแตกลงไปหาปัญหาย่อย เหมือนเดิม — "จากบนลงล่าง")
เพียงแต่เพิ่ม "ตารางจดจำ" (เรียกว่า **Memo Table** หรือ **Cache**) เข้าไปเท่านั้น

### โค้ดสมบูรณ์

```c
/* ============================================================
 * ชื่อไฟล์:     fib_memo.c
 * คำอธิบาย:     Fibonacci ด้วย Memoization (Top-down DP)
 * ============================================================ */

/* ---------- 1. Header Includes ---------- */
#include <stdio.h>

/* ---------- 2. Macro / Constant Definitions ---------- */
#define MAX_N 50
#define NOT_COMPUTED (-1L)

/* ---------- 3. Global Memo Table และ Function Prototypes ---------- */
long memo[MAX_N + 1];
long call_count = 0;

long fib_memo(int n);

/* ---------- 4. main() ---------- */
int main(void) {
    for (int i = 0; i <= MAX_N; i++) {
        memo[i] = NOT_COMPUTED; /* เริ่มต้น: ยังไม่เคยคำนวณค่าไหนเลย */
    }

    call_count = 0;
    long result = fib_memo(40);
    printf("fib(40) = %ld (เรียกฟังก์ชันจริงเพียง %ld ครั้ง)\n", result, call_count);

    return 0;
}

/* ---------- 5. Function Implementations ---------- */
long fib_memo(int n) {
    call_count++;

    if (n <= 1) {
        return n; /* Base Case เหมือน Naive Fibonacci ทุกประการ */
    }

    /* ถ้าเคยคำนวณค่านี้ไว้แล้ว ให้ใช้ค่าเดิมทันที ไม่ต้องคำนวณซ้ำ */
    if (memo[n] != NOT_COMPUTED) {
        return memo[n];
    }

    /* คำนวณครั้งแรก แล้วบันทึกผลลัพธ์ลง memo[] ก่อนคืนค่า */
    memo[n] = fib_memo(n - 1) + fib_memo(n - 2);
    return memo[n];
}
```

```bash
gcc -Wall -Wextra -Wpedantic -std=c17 fib_memo.c -o fib_memo
./fib_memo
```

```
fib(40) = 102334155 (เรียกฟังก์ชันจริงเพียง 79 ครั้ง)
```

เปรียบเทียบให้เห็นภาพชัด: `fib_naive(40)` ต้องเรียกฟังก์ชันประมาณ **331 ล้านครั้ง** แต่
`fib_memo(40)` เรียกเพียง **79 ครั้ง** เท่านั้น! ลดลงมากกว่า **4 ล้านเท่า** จากการเพิ่ม
เงื่อนไขตรวจสอบ Memo Table เข้าไปเพียงไม่กี่บรรทัด

### วิเคราะห์ความซับซ้อนใหม่

ทุกค่า `fib(0)` ถึง `fib(n)` จะถูก**คำนวณจริงเพียงครั้งเดียว** เท่านั้น (ครั้งต่อๆ ไปดึงจาก
`memo[]` แทน ซึ่งเป็น O(1)) ดังนั้นจำนวนการคำนวณจริงทั้งหมดคือ `n+1` ค่า → ความซับซ้อนลดลง
จาก **O(2ⁿ)** เหลือ **O(n)** เท่านั้น — เป็นการพิสูจน์อย่างเป็นรูปธรรมว่า Dynamic Programming
สามารถเปลี่ยนอัลกอริทึมจาก "ใช้งานไม่ได้จริง" ให้กลายเป็น "เร็วมาก" ได้เพียงแค่เพิ่มเทคนิค
การจดจำผลลัพธ์ที่เคยคำนวณแล้ว

### Recursion Tree หลังใส่ Memoization

```
                              fib(5)
                          /            \
                     fib(4)              fib(3) <- มีใน memo แล้ว! คืนค่าทันที ไม่แตกกิ่งต่อ
                    /      \
               fib(3)      fib(2) <- มีใน memo แล้ว! คืนค่าทันที
               /    \
          fib(2)  fib(1) <- มีใน memo แล้ว! คืนค่าทันที
          /    \
       fib(1) fib(0)
```

สังเกตว่า Recursion Tree ที่เคยแตกกิ่งมหาศาลตอนนี้ถูก "ตัดกิ่งที่ซ้ำ" ทิ้งไปเกือบหมด เหลือ
เพียงเส้นทางที่จำเป็นต้องคำนวณจริงเท่านั้น — รูปร่างของต้นไม้เปลี่ยนจาก Exponential กลายเป็น
เกือบ Linear ทันที

## 25.4 Tabulation: Bottom-up Dynamic Programming (Step 196)

**Tabulation** คือแนวทางที่ตรงข้ามกับ Memoization ในเชิงทิศทาง: แทนที่จะเริ่มจากปัญหาใหญ่แล้ว
แตกลงไปหาปัญหาย่อย (Top-down) เราจะ **เริ่มจากปัญหาย่อยที่สุดก่อน** แล้วค่อยๆ สร้างคำตอบขึ้นไป
จนถึงปัญหาใหญ่ที่ต้องการ (เรียกว่า **Bottom-up**) — และที่สำคัญคือ **ไม่ต้องใช้ Recursion เลย**
ใช้แค่ Loop ธรรมดา

### โค้ดสมบูรณ์

```c
/* ============================================================
 * ชื่อไฟล์:     fib_tabulation.c
 * คำอธิบาย:     Fibonacci ด้วย Tabulation (Bottom-up DP) ไม่ใช้ Recursion เลย
 * ============================================================ */
#include <stdio.h>

long fib_tabulation(int n);

int main(void) {
    for (int i = 0; i <= 10; i++) {
        printf("fib(%2d) = %ld\n", i, fib_tabulation(i));
    }
    return 0;
}

long fib_tabulation(int n) {
    if (n <= 1) {
        return n;
    }

    long prev2 = 0; /* เก็บค่า fib(0) */
    long prev1 = 1; /* เก็บค่า fib(1) */
    long current = 0;

    /* ไล่สร้างคำตอบจาก fib(2) ขึ้นไปจนถึง fib(n) ทีละขั้น */
    for (int i = 2; i <= n; i++) {
        current = prev1 + prev2;
        prev2 = prev1;
        prev1 = current;
    }

    return current;
}
```

```bash
gcc -Wall -Wextra -Wpedantic -std=c17 fib_tabulation.c -o fib_tabulation
./fib_tabulation
```

```
fib( 0) = 0
fib( 1) = 1
fib( 2) = 1
fib( 3) = 2
fib( 4) = 3
fib( 5) = 5
fib( 6) = 8
fib( 7) = 13
fib( 8) = 21
fib( 9) = 34
fib(10) = 55
```

### Trace การทำงานของ fib_tabulation(6)

```
เริ่มต้น: prev2=0 (fib(0)), prev1=1 (fib(1))

i=2: current = prev1+prev2 = 1+0 = 1   (fib(2))   -> prev2=1, prev1=1
i=3: current = prev1+prev2 = 1+1 = 2   (fib(3))   -> prev2=1, prev1=2
i=4: current = prev1+prev2 = 2+1 = 3   (fib(4))   -> prev2=2, prev1=3
i=5: current = prev1+prev2 = 3+2 = 5   (fib(5))   -> prev2=3, prev1=5
i=6: current = prev1+prev2 = 5+3 = 8   (fib(6))   -> prev2=5, prev1=8

ผลลัพธ์: fib(6) = 8  (ตรงกับตารางในหัวข้อ 25.2)
```

### เปรียบเทียบ Memoization กับ Tabulation

| ประเด็น | Memoization (Top-down) | Tabulation (Bottom-up) |
|---|---|---|
| ทิศทางการคำนวณ | เริ่มจากปัญหาใหญ่ แตกลงหาปัญหาย่อย | เริ่มจากปัญหาย่อยที่สุด สร้างขึ้นไปหาปัญหาใหญ่ |
| ใช้ Recursion หรือไม่ | ใช้ (มี Call Stack) | ไม่ใช้ (เป็น Loop ล้วนๆ) |
| ความเสี่ยง Stack Overflow | มี ถ้า `n` ใหญ่มากจน Call Stack ล้น | ไม่มี เพราะไม่มีการเรียกซ้อนกันเลย |
| หน่วยความจำที่ใช้ | ต้องเก็บทุกค่าที่เคยคำนวณไว้ใน Memo Table | ในหลายกรณีลดขนาดหน่วยความจำได้ (เช่น Fibonacci เก็บแค่ 2 ค่าล่าสุดพอ ไม่ต้องเก็บทั้งอาร์เรย์) |
| คำนวณเฉพาะที่จำเป็นหรือไม่ | คำนวณเฉพาะปัญหาย่อยที่ถูกเรียกถึงจริงเท่านั้น | คำนวณทุกปัญหาย่อยตั้งแต่เล็กสุดถึงใหญ่สุดเสมอ แม้บางค่าอาจไม่จำเป็น |
| เขียนโค้ดง่ายกว่าแบบไหน | มักเขียนง่ายกว่า เพราะแปลงจากนิยาม Recursive ตรงๆ | บางปัญหาต้องคิดลำดับการเติมตารางให้ถูกต้อง อาจซับซ้อนกว่าตอนเริ่มต้น |

ในทางปฏิบัติ **Tabulation มักเร็วกว่าเล็กน้อย** เพราะไม่มี Overhead ของการเรียกฟังก์ชัน
(Function Call Overhead) จาก Recursion และไม่มีความเสี่ยง Stack Overflow แต่ **Memoization
เขียนง่ายกว่าและเป็นธรรมชาติกว่า** สำหรับปัญหาที่นิยามด้วย Recursion อยู่แล้ว — ทั้งสองแบบ
ให้ความซับซ้อนเวลาเท่ากันคือ **O(n)** สำหรับ Fibonacci

## 25.5 วิธีสังเกตว่าปัญหาหนึ่งเหมาะกับ Dynamic Programming (Step 197)

ไม่ใช่ทุกปัญหาที่มี Recursion จะได้ประโยชน์จาก Dynamic Programming — ต้องมีคุณสมบัติ 2 ข้อ
ครบทั้งคู่ปัญหาถึงจะเหมาะสม:

### เงื่อนไขที่ 1: Overlapping Subproblems (ปัญหาย่อยที่ซ้อนทับกัน)

ปัญหาใหญ่สามารถแตกเป็นปัญหาย่อยที่ **มีปัญหาย่อยบางตัวถูกคำนวณซ้ำหลายครั้ง** เมื่อแก้แบบ
Recursive ตรงไปตรงมา — ดังที่เห็นใน Recursion Tree ของ Fibonacci (หัวข้อ 25.2) ที่ `fib(3)`,
`fib(2)` ถูกคำนวณซ้ำหลายครั้ง

**วิธีตรวจสอบ**: ลองวาด Recursion Tree ของปัญหา (หรือจินตนาการดู) แล้วดูว่ามี Node ไหนที่
มีค่าพารามิเตอร์ซ้ำกันปรากฏหลายครั้งหรือไม่ ถ้ามี → ผ่านเงื่อนไขข้อนี้

**ตัวอย่างปัญหาที่ไม่มี Overlapping Subproblems**: Merge Sort (Part 23) — แม้จะเป็น Divide
and Conquer เหมือนกัน แต่ปัญหาย่อยแต่ละตัว (แต่ละครึ่งของอาร์เรย์) **ไม่เคยซ้ำกันเลย** เพราะ
เป็นคนละช่วง index กัน จึงไม่ได้ประโยชน์จาก Memoization และ Merge Sort ก็ไม่ใช่ปัญหา DP

### เงื่อนไขที่ 2: Optimal Substructure (โครงสร้างคำตอบที่เหมาะสมที่สุด)

คำตอบที่ดีที่สุด (Optimal Solution) ของปัญหาใหญ่ สามารถสร้างขึ้นได้จาก **คำตอบที่ดีที่สุด
ของปัญหาย่อย** โดยตรง — พูดง่ายๆ คือ "ถ้าแก้ปัญหาย่อยให้ดีที่สุดแล้ว เอามาประกอบกันจะได้
คำตอบที่ดีที่สุดของปัญหาใหญ่ด้วย"

**ตัวอย่าง**: ใน 0/1 Knapsack (หัวข้อ 25.6) คำตอบที่ดีที่สุดสำหรับ "ของ n ชิ้น ความจุ W"
สร้างได้จากคำตอบที่ดีที่สุดของ "ของ n-1 ชิ้น ความจุ W" (กรณีไม่หยิบของชิ้นที่ n) เปรียบเทียบ
กับ "ของ n-1 ชิ้น ความจุ W - น้ำหนักของชิ้นที่ n บวกมูลค่าของชิ้นที่ n" (กรณีหยิบของชิ้นที่ n)

### ตารางสรุปวิธีสังเกตปัญหา DP อย่างรวดเร็ว

| สัญญาณที่บ่งบอกว่าอาจเป็นปัญหา DP | ตัวอย่าง |
|---|---|
| โจทย์ถามหา "ค่ามากที่สุด/น้อยที่สุด/จำนวนวิธี" ภายใต้เงื่อนไขบางอย่าง | Knapsack (มูลค่ามากที่สุด), จำนวนวิธีขึ้นบันได |
| แก้ปัญหาด้วย Recursive ตรงไปตรงมาแล้วช้ามาก (สงสัยว่า Exponential) | Naive Fibonacci |
| ปัญหาสามารถนิยามด้วยตัวแปรสถานะ (State) จำนวนไม่มาก เช่น (ตำแหน่งที่ i, ความจุที่เหลือ w) | Knapsack: state คือ (i, w) |
| คำตอบของปัญหาขนาด n สร้างจากคำตอบของปัญหาขนาดเล็กกว่า (n-1, n/2, ฯลฯ) ได้ | LCS, Fibonacci |

ในหัวข้อถัดไปเราจะนำแนวคิดนี้ไปใช้แก้ปัญหาคลาสสิก 2 ข้อที่เป็นรากฐานสำคัญของวิชา Algorithm:
**0/1 Knapsack** และ **Longest Common Subsequence**

## 25.6 0/1 Knapsack Problem (Step 198)

**โจทย์**: มีของ `n` ชิ้น แต่ละชิ้นมี **น้ำหนัก (weight)** และ **มูลค่า (value)** ที่แน่นอน
เรามีกระเป๋าที่รับน้ำหนักได้สูงสุด `W` หน่วย ต้องการเลือกของบางชิ้นใส่กระเป๋าให้ได้ **มูลค่า
รวมมากที่สุด** โดยที่น้ำหนักรวมต้องไม่เกิน `W` — เงื่อนไขสำคัญคือ **แต่ละชิ้นเลือกได้แค่
"หยิบ" หรือ "ไม่หยิบ"** เท่านั้น (จะหยิบครึ่งชิ้นไม่ได้ นี่คือที่มาของชื่อ "0/1")

### วิเคราะห์ตามเงื่อนไข DP

- **Optimal Substructure**: ถ้าเรารู้คำตอบที่ดีที่สุดสำหรับ "ของ i-1 ชิ้นแรก ความจุ w" แล้ว
  เราสามารถตัดสินใจเรื่องของชิ้นที่ `i` ได้ทันทีโดยเปรียบเทียบ 2 ทางเลือก
- **Overlapping Subproblems**: คำนวณ Recursive ตรงๆ จะพบว่าปัญหาย่อย (i, w) ซ้ำกันซ้ำแล้ว
  ซ้ำเล่าหลายเส้นทาง (คล้าย Fibonacci)

### สูตร Recurrence

กำหนดให้ `dp[i][w]` = มูลค่าสูงสุดที่ได้เมื่อพิจารณาของ `i` ชิ้นแรก และความจุกระเป๋าไม่เกิน
`w`:

```
dp[i][w] = 0                                              ถ้า i == 0 หรือ w == 0
dp[i][w] = dp[i-1][w]                                     ถ้าของชิ้นที่ i หนักเกิน w
dp[i][w] = max( dp[i-1][w],                               (ไม่หยิบของชิ้นที่ i)
                values[i-1] + dp[i-1][w - weights[i-1]] ) (หยิบของชิ้นที่ i)
```

### โค้ดสมบูรณ์

```c
/* ============================================================
 * ชื่อไฟล์:     knapsack.c
 * คำอธิบาย:     แก้ปัญหา 0/1 Knapsack ด้วย Dynamic Programming (Tabulation)
 * ============================================================ */

/* ---------- 1. Header Includes ---------- */
#include <stdio.h>

/* ---------- 2. Macro / Constant Definitions ---------- */
#define NUM_ITEMS 4
#define CAPACITY 8

/* ---------- 3. Function Prototypes ---------- */
int max_int(int a, int b);
int knapsack_01(int capacity, const int weights[], const int values[], int n);

/* ---------- 4. main() ---------- */
int main(void) {
    /* ของ 4 ชิ้น: (น้ำหนัก, มูลค่า) = (2,3), (3,4), (4,5), (5,6) */
    int weights[NUM_ITEMS] = {2, 3, 4, 5};
    int values[NUM_ITEMS]  = {3, 4, 5, 6};

    int best_value = knapsack_01(CAPACITY, weights, values, NUM_ITEMS);

    printf("กระเป๋ารับน้ำหนักได้สูงสุด %d หน่วย\n", CAPACITY);
    printf("มูลค่าสูงสุดที่หยิบได้ = %d\n", best_value);

    return 0;
}

/* ---------- 5. Function Implementations ---------- */
int max_int(int a, int b) {
    return (a > b) ? a : b;
}

int knapsack_01(int capacity, const int weights[], const int values[], int n) {
    /* dp[i][w] = มูลค่าสูงสุดที่ได้เมื่อพิจารณาของ i ชิ้นแรก และน้ำหนักไม่เกิน w */
    int dp[NUM_ITEMS + 1][CAPACITY + 1];

    for (int i = 0; i <= n; i++) {
        for (int w = 0; w <= capacity; w++) {
            if (i == 0 || w == 0) {
                dp[i][w] = 0; /* ไม่มีของให้เลือก หรือกระเป๋าจุอะไรไม่ได้เลย */
            } else if (weights[i - 1] <= w) {
                /* เลือกตัวเลือกที่ดีที่สุด: หยิบของชิ้นนี้ หรือ ไม่หยิบ */
                int take = values[i - 1] + dp[i - 1][w - weights[i - 1]];
                int skip = dp[i - 1][w];
                dp[i][w] = max_int(take, skip);
            } else {
                /* ของชิ้นนี้หนักเกินความจุที่เหลือ หยิบไม่ได้ ใช้คำตอบเดิมจากของ i-1 ชิ้น */
                dp[i][w] = dp[i - 1][w];
            }
        }
    }

    return dp[n][capacity];
}
```

```bash
gcc -Wall -Wextra -Wpedantic -std=c17 knapsack.c -o knapsack
./knapsack
```

### ตรวจคำตอบด้วยมือ

ของ 4 ชิ้น: `(w=2,v=3)`, `(w=3,v=4)`, `(w=4,v=5)`, `(w=5,v=6)` ความจุกระเป๋า = 8

ลองพิจารณาชุดค่าผสมที่เป็นไปได้ทั้งหมดที่น้ำหนักไม่เกิน 8:

```
หยิบชิ้น 2+4 (w=3+5=8, v=4+6=10)  <- มูลค่าสูงสุด!
หยิบชิ้น 1+3 (w=2+4=6, v=3+5=8)
หยิบชิ้น 1+4 (w=2+5=7, v=3+6=9)
หยิบชิ้น 2+3 (w=3+4=7, v=4+5=9)
หยิบชิ้น 1+2 (w=2+3=5, v=3+4=7)
หยิบชิ้น 3+4 (w=4+5=9 > 8, ไม่ได้เพราะเกินความจุ)
```

คำตอบที่ดีที่สุดคือหยิบชิ้นที่ 2 กับชิ้นที่ 4 ได้มูลค่า **10** ตรงกับผลลัพธ์ที่โปรแกรมคำนวณได้

### วิเคราะห์ความซับซ้อน

ตาราง `dp[i][w]` มีขนาด `(n+1) × (W+1)` และแต่ละช่องใช้เวลาคำนวณ O(1) (แค่เปรียบเทียบ 2 ค่า)
ดังนั้นความซับซ้อนโดยรวมคือ **O(n × W)** — เรียกว่า **Pseudo-polynomial Time** เพราะขึ้นกับ
**ค่า** ของ `W` (ไม่ใช่แค่จำนวนบิตที่ใช้แทน `W`) ถ้า `W` มีค่ามหาศาล (เช่นพันล้าน) วิธีนี้จะ
ใช้หน่วยความจำและเวลามหาศาลตามไปด้วย แต่สำหรับ `W` ขนาดพอเหมาะ (เช่นหลักพันถึงหลักหมื่น)
วิธีนี้เร็วกว่าการลองทุกชุดค่าผสม (Brute Force ที่มีความซับซ้อน O(2ⁿ)) อย่างมหาศาล

## 25.7 Longest Common Subsequence (LCS) (Step 199)

**โจทย์**: กำหนด String สองตัว หา **Subsequence ร่วมที่ยาวที่สุด** — Subsequence คือลำดับ
ตัวอักษรที่ดึงออกมาจาก String ต้นฉบับโดย**ไม่จำเป็นต้องติดกัน** แต่ต้อง**คงลำดับเดิมไว้**

ตัวอย่าง: `"ABCBDAB"` และ `"BDCABA"` — คำตอบคือ `"BCBA"` (ความยาว 4) เพราะ:

```
A B C B D A B     <- string A, ตำแหน่งที่เลือก: B(2) C(3) B(4) A(6)
    ↓   ↓ ↓   ↓
  B   C B   A       (ไล่จากซ้ายไปขวา ตามลำดับเดิม)

B D C A B A       <- string B, ตำแหน่งที่เลือก: B(1) C(3) B(5) A(6)
  ↓   ↓     ↓ ↓
    C   B   A
```

LCS เป็นปัญหาพื้นฐานที่ใช้จริงในหลายวงการ: **`diff`** (เปรียบเทียบไฟล์ใน Git), การเปรียบเทียบ
สาย DNA ในชีวสารสนเทศศาสตร์ (Bioinformatics), ระบบตรวจจับการลอกเลียน (Plagiarism Detection)

### วิเคราะห์ตามเงื่อนไข DP

กำหนดให้ `dp[i][j]` = ความยาวของ LCS ระหว่าง `a[0..i-1]` กับ `b[0..j-1]` (String A ตัดมา
`i` ตัวแรก, String B ตัดมา `j` ตัวแรก)

### สูตร Recurrence

```
dp[i][j] = 0                                ถ้า i == 0 หรือ j == 0
dp[i][j] = dp[i-1][j-1] + 1                 ถ้า a[i-1] == b[j-1]  (ตัวอักษรตรงกัน ต่อความยาวได้)
dp[i][j] = max(dp[i-1][j], dp[i][j-1])      ถ้า a[i-1] != b[j-1]  (ไม่ตรงกัน เลือกทางที่ดีกว่า)
```

### โค้ดสมบูรณ์ (คำนวณความยาว + สร้างสาย LCS จริงกลับมา)

```c
/* ============================================================
 * ชื่อไฟล์:     lcs.c
 * คำอธิบาย:     หา Longest Common Subsequence ด้วย Dynamic Programming
 * ============================================================ */
#include <stdio.h>
#include <string.h>

#define MAX_LEN 100

int max_int(int a, int b) {
    return (a > b) ? a : b;
}

int lcs_length(const char *a, const char *b, int dp[MAX_LEN + 1][MAX_LEN + 1]) {
    int len_a = (int)strlen(a);
    int len_b = (int)strlen(b);

    for (int i = 0; i <= len_a; i++) {
        for (int j = 0; j <= len_b; j++) {
            if (i == 0 || j == 0) {
                dp[i][j] = 0;
            } else if (a[i - 1] == b[j - 1]) {
                dp[i][j] = dp[i - 1][j - 1] + 1;
            } else {
                dp[i][j] = max_int(dp[i - 1][j], dp[i][j - 1]);
            }
        }
    }

    return dp[len_a][len_b];
}

/* ย้อนรอยจากตาราง dp[][] เพื่อสร้างสาย LCS ตัวจริงกลับคืนมา ไม่ใช่แค่ความยาว */
void print_lcs(const char *a, const char *b, int dp[MAX_LEN + 1][MAX_LEN + 1]) {
    int i = (int)strlen(a);
    int j = (int)strlen(b);
    char result[MAX_LEN];
    int pos = dp[i][j]; /* ความยาวของ LCS คือตำแหน่งสุดท้ายของ result (ก่อน '\0') */

    result[pos] = '\0';

    while (i > 0 && j > 0) {
        if (a[i - 1] == b[j - 1]) {
            /* ตัวอักษรตรงกัน แปลว่าตัวนี้เป็นส่วนหนึ่งของ LCS แน่นอน */
            pos--;
            result[pos] = a[i - 1];
            i--;
            j--;
        } else if (dp[i - 1][j] >= dp[i][j - 1]) {
            i--; /* เดินตามทิศทางที่ dp[][] มีค่ามากกว่า (มาจากการตัดสินใจตอนคำนวณ) */
        } else {
            j--;
        }
    }

    printf("LCS ที่แท้จริงคือ: \"%s\"\n", result);
}

int main(void) {
    const char *str_a = "ABCBDAB";
    const char *str_b = "BDCABA";

    static int dp[MAX_LEN + 1][MAX_LEN + 1];

    int length = lcs_length(str_a, str_b, dp);

    printf("string A = \"%s\"\n", str_a);
    printf("string B = \"%s\"\n", str_b);
    printf("ความยาว LCS = %d\n", length);
    print_lcs(str_a, str_b, dp);

    return 0;
}
```

## 25.8 สรุปเปรียบเทียบและเมื่อไหร่ควรใช้ Dynamic Programming (Step 200)

### ตารางสรุปทุกปัญหาที่เรียนใน Part นี้

| ปัญหา | Brute Force / Naive | หลัง Dynamic Programming | เทคนิคที่ใช้ |
|---|---|---|---|
| Fibonacci | O(2ⁿ) | O(n) | Memoization หรือ Tabulation |
| 0/1 Knapsack | O(2ⁿ) (ลองทุกชุดค่าผสม) | O(n × W) | Tabulation แบบ 2 มิติ |
| Longest Common Subsequence | O(2ⁿ) (ลองทุก Subsequence) | O(n × m) | Tabulation แบบ 2 มิติ + Backtracking |

### ขั้นตอนมาตรฐานในการแก้ปัญหา Dynamic Programming

เมื่อเจอปัญหาที่สงสัยว่าเป็น DP ให้ทำตามขั้นตอนนี้เสมอ:

1. **นิยาม State**: ปัญหาย่อยของเราคืออะไร ต้องใช้ตัวแปรกี่ตัวมาระบุปัญหาย่อยหนึ่งๆ (เช่น
   Fibonacci ใช้แค่ `n` ตัวเดียว, Knapsack ใช้ `(i, w)` สองตัว, LCS ใช้ `(i, j)` สองตัว)
2. **หาสูตร Recurrence**: คำตอบของปัญหาปัจจุบันสัมพันธ์กับคำตอบของปัญหาย่อยที่เล็กกว่าอย่างไร
3. **หา Base Case**: ปัญหาย่อยที่เล็กที่สุดที่ตอบได้ทันทีโดยไม่ต้องพึ่งปัญหาอื่นคืออะไร
4. **ตัดสินใจ Top-down หรือ Bottom-up**: จะเขียนแบบ Memoization (เขียนง่ายกว่า เหมาะกับ
   ปัญหาที่ไม่ได้ต้องการทุก State) หรือ Tabulation (เร็วกว่า ไม่มี Stack Overflow เหมาะกับ
   ปัญหาที่ต้องการ State เกือบทั้งหมดอยู่แล้ว)
5. **ตรวจสอบ Space Optimization**: บางปัญหาไม่จำเป็นต้องเก็บตารางทั้งหมด เก็บแค่แถว/ค่า
   ล่าสุดที่จำเป็นก็พอ (เหมือน `fib_tabulation()` ที่เก็บแค่ 2 ตัวแปร ไม่ต้องมีอาร์เรย์เต็ม)

### เมื่อไหร่ไม่ควรใช้ Dynamic Programming

- **ปัญหาไม่มี Overlapping Subproblems**: เช่น Merge Sort — ใช้ Divide and Conquer ธรรมดา
  ก็เพียงพอแล้ว ไม่ได้ประโยชน์จาก Memoization
- **ปัญหาต้องการแค่คำตอบเดียวจากปัญหาย่อยเฉพาะเจาะจง ไม่ใช่ทุก State**: บางครั้ง Greedy
  Algorithm (อัลกอริทึมโลภที่เลือกทางเลือกที่ดีที่สุด ณ ขณะนั้นโดยไม่ย้อนกลับ) อาจให้คำตอบ
  ที่ถูกต้องและเร็วกว่า DP มาก (แต่ต้องพิสูจน์ก่อนว่า Greedy ใช้ได้กับปัญหานั้นจริง — ไม่ใช่
  ทุกปัญหาที่ Greedy จะให้คำตอบที่ถูกต้อง)
- **State Space ใหญ่เกินไป**: ถ้าจำนวน State ที่เป็นไปได้มีมากเกินกว่าจะเก็บในหน่วยความจำ
  (เช่น Knapsack ที่ `W` เป็นตัวเลขขนาดใหญ่มาก) อาจต้องหาวิธีอื่น เช่น Approximation Algorithm

## ข้อผิดพลาดที่พบบ่อย (Common Pitfalls)

1. **ลืมกำหนดค่าเริ่มต้นของ Memo Table ให้เป็นค่าที่ "ไม่มีทางเป็นคำตอบจริง"** เช่นใช้ `0`
   เป็นค่าเริ่มต้นของ `memo[]` ทั้งที่ `0` อาจเป็นคำตอบจริงของปัญหาบางตัวได้ (เช่น `fib(0) = 0`)
   ทำให้ตรวจสอบผิดพลาดว่า "เคยคำนวณแล้ว" ทั้งที่จริงยังไม่เคย — ควรใช้ค่าพิเศษที่ไม่มีทางเป็น
   คำตอบจริง เช่น `-1` (ดังในโค้ด `fib_memo.c` ที่ใช้ `NOT_COMPUTED`)

2. **ประกาศอาร์เรย์ 2 มิติขนาดใหญ่บน Stack โดยตรง** เช่น `int dp[10000][10000];` ใน `main()`
   จะทำให้เกิด **Stack Overflow** ทันทีตอนโปรแกรมเริ่มทำงาน (Segmentation Fault) เพราะ
   ขนาด Stack มีจำกัด ควรใช้ `static` หรือจองด้วย `malloc` แทนสำหรับอาร์เรย์ขนาดใหญ่

3. **สับสนระหว่าง Index ของ String กับ Index ของตาราง `dp[][]`** ใน LCS — สูตร `dp[i][j]`
   หมายถึง "พิจารณา `a[0..i-1]`" ไม่ใช่ `a[0..i]` เพราะ `dp` มีขนาด `(len+1)` เพื่อรองรับ
   กรณี "ยังไม่พิจารณาตัวอักษรใดเลย" (`i == 0`) — การเขียน `a[i]` แทน `a[i-1]` ตรงนี้เป็น
   ข้อผิดพลาดที่พบบ่อยที่สุดของมือใหม่ที่เขียน LCS

4. **ลืม Base Case ของ Dynamic Programming** เช่นลืมเซ็ต `dp[i][0]` และ `dp[0][j]` ให้เป็น 0
   ก่อน (ในกรณีที่ไม่ได้ initialize ตารางไว้เป็น 0 ตั้งแต่แรก) ทำให้ค่าที่อ่านได้เป็นขยะ
   (Garbage Value) จากหน่วยความจำที่ยังไม่ได้กำหนดค่า

5. **ใช้ Recursion แบบ Memoization กับปัญหาที่มี `n` ใหญ่มาก โดยไม่ระวังขนาด Call Stack**
   แม้ Memoization จะลดจำนวนการเรียกฟังก์ชันทั้งหมด แต่ **ความลึกของ Call Stack ในเส้นทาง
   แรกที่ยังไม่มีอะไรใน Memo Table เลย** ยังคงเท่ากับ `n` เสมอ ถ้า `n` มีค่ามากถึงหลักแสนหรือ
   ล้าน อาจเกิด Stack Overflow ได้ — กรณีแบบนี้ควรใช้ Tabulation แทน

6. **คิดว่า Dynamic Programming ใช้ได้กับทุกปัญหาที่มี Recursion** โดยไม่ตรวจสอบเงื่อนไข
   Overlapping Subproblems และ Optimal Substructure ก่อน ทำให้เสียเวลาเขียน Memo Table
   สำหรับปัญหาที่ไม่ได้ประโยชน์อะไรเลย (เช่น Merge Sort, Binary Search)

7. **ลืมว่า `weights[i - 1]` และ `values[i - 1]` ใน Knapsack คือของชิ้นที่ i (นับจาก 1)
   ไม่ใช่ของชิ้นที่ i (นับจาก 0)** เพราะ `dp[i][w]` นิยามว่า "พิจารณาของ `i` ชิ้นแรก" แต่
   อาร์เรย์ `weights[]`/`values[]` เก็บข้อมูลแบบ 0-indexed ตามปกติของ C — จุดนี้ทำให้เกิด
   Off-by-one Error ได้ง่ายถ้าไม่ระวัง

   เก็บทุกค่ากับการเก็บแค่ 2 ค่าล่าสุด

3. เขียนโปรแกรมที่แก้ปัญหา **"จำนวนวิธีขึ้นบันได n ขั้น โดยแต่ละครั้งก้าวได้ 1 หรือ 2 ขั้น"**
   ด้วย Dynamic Programming (คำใบ้: สูตร Recurrence คล้าย Fibonacci มาก — `ways(n) =
   ways(n-1) + ways(n-2)`)

4. ดัดแปลง `knapsack.c` ให้พิมพ์ **รายการของที่ควรหยิบจริง** (ไม่ใช่แค่มูลค่าสูงสุด) โดยใช้
   เทคนิคย้อนรอย (Backtracking) จากตาราง `dp[][]` คล้ายกับที่ `print_lcs()` ทำ

5. เขียนฟังก์ชัน `lcs_length_optimized()` ที่คำนวณ **ความยาว** ของ LCS เท่านั้น (ไม่ต้อง
   ย้อนรอยหาสายจริง) โดยใช้หน่วยความจำแค่ O(min(len_a, len_b)) แทนที่จะเป็น O(len_a × len_b)
   เต็มตาราง

6. จงพิจารณาปัญหา **"หาผลรวมย่อยของอาร์เรย์ที่ต่อเนื่องกัน (Contiguous Subarray) ที่มีค่ามาก
   ที่สุด" (Maximum Subarray Sum)** แล้ววิเคราะห์ว่าปัญหานี้มี Overlapping Subproblems และ
   Optimal Substructure หรือไม่ พร้อมเขียนโปรแกรมแก้ปัญหานี้ด้วย Dynamic Programming

```c
/* ============================================================
 * ชื่อไฟล์:     climbing_stairs.c
 * คำอธิบาย:     นับจำนวนวิธีขึ้นบันได n ขั้น (ก้าวได้ครั้งละ 1 หรือ 2 ขั้น) ด้วย DP
 * ============================================================ */
#include <stdio.h>

long count_ways_tabulation(int n);

int main(void) {
    for (int n = 1; n <= 10; n++) {
        printf("บันได %2d ขั้น มีวิธีขึ้นได้ %ld วิธี\n", n, count_ways_tabulation(n));
    }
    return 0;
}

long count_ways_tabulation(int n) {
    /* Base Case: บันได 0 ขั้น มี 1 วิธี (คือไม่ต้องก้าวเลย)
       บันได 1 ขั้น มี 1 วิธี (ก้าวทีเดียว 1 ขั้น) */
    if (n == 0 || n == 1) {
        return 1;
    }

    long prev2 = 1; /* ways(0) */
    long prev1 = 1; /* ways(1) */
    long current = 0;

    /* วิธีขึ้นบันไดขั้นที่ i ได้ = วิธีขึ้นถึงขั้น i-1 (แล้วก้าว 1 ขั้น)
                                  + วิธีขึ้นถึงขั้น i-2 (แล้วก้าว 2 ขั้น)
       ซึ่งเป็นสูตร Recurrence แบบเดียวกับ Fibonacci เป๊ะ */
    for (int i = 2; i <= n; i++) {
        current = prev1 + prev2;
        prev2 = prev1;
        prev1 = current;
    }

    return current;
}
```

### แนวทางเฉลยข้อ 5

```c
/* ============================================================
 * ชื่อไฟล์:     lcs_length_optimized.c
 * คำอธิบาย:     หาความยาว LCS ด้วยหน่วยความจำ O(min(len_a, len_b)) แทน O(len_a * len_b)
 * ============================================================ */
#include <stdio.h>
#include <string.h>

#define MAX_LEN 100

int max_int(int a, int b) {
    return (a > b) ? a : b;
}

int lcs_length_optimized(const char *a, const char *b) {
    int len_a = (int)strlen(a);
    int len_b = (int)strlen(b);

    /* เก็บแค่ 2 แถว (แถวปัจจุบันและแถวก่อนหน้า) แทนที่จะเก็บทั้งตาราง (len_a+1) x (len_b+1) */
    int prev_row[MAX_LEN + 1];
    int curr_row[MAX_LEN + 1];

    for (int j = 0; j <= len_b; j++) {
        prev_row[j] = 0; /* แถวฐาน: dp[0][j] = 0 เสมอ */
    }

    for (int i = 1; i <= len_a; i++) {
        curr_row[0] = 0; /* คอลัมน์ฐาน: dp[i][0] = 0 เสมอ */

        for (int j = 1; j <= len_b; j++) {
            if (a[i - 1] == b[j - 1]) {
                curr_row[j] = prev_row[j - 1] + 1;
            } else {
                curr_row[j] = max_int(prev_row[j], curr_row[j - 1]);
            }
        }

        /* เลื่อนแถวปัจจุบันไปเป็นแถวก่อนหน้า สำหรับรอบถัดไป */
        for (int j = 0; j <= len_b; j++) {
            prev_row[j] = curr_row[j];
        }
    }

    return prev_row[len_b];
}

int main(void) {
    const char *str_a = "ABCBDAB";
    const char *str_b = "BDCABA";

    int length = lcs_length_optimized(str_a, str_b);

    printf("string A = \"%s\"\n", str_a);
    printf("string B = \"%s\"\n", str_b);
    printf("ความยาว LCS (แบบใช้หน่วยความจำน้อยลง) = %d\n", length);

    return 0;
}
```

**คำอธิบาย**: สังเกตว่าในการคำนวณ `dp[i][j]` เราต้องการแค่ค่าจาก **แถว `i-1`** (คือ
`dp[i-1][j]` และ `dp[i-1][j-1]`) และค่าจาก **แถวปัจจุบัน `i`** ทางซ้ายมือ (`dp[i][j-1]`)
เท่านั้น — ไม่เคยต้องย้อนกลับไปดูแถวที่เก่ากว่า `i-1` เลย ดังนั้นเราจึงไม่จำเป็นต้องเก็บ
ทั้งตาราง 2 มิติ เก็บแค่ 2 แถวสลับกันไปมาก็เพียงพอ ทำให้ Space Complexity ลดลงจาก
**O(len_a × len_b)** เหลือ **O(len_b)** เท่านั้น (แลกกับการที่ไม่สามารถย้อนรอยหาสาย LCS
จริงได้อีกต่อไป เพราะข้อมูลแถวเก่าถูกเขียนทับไปแล้ว) — นี่คือตัวอย่างของ **Space Optimization**
ที่กล่าวถึงในขั้นตอนที่ 5 ของหัวข้อ 25.8

## สรุปท้ายบท

ใน Part นี้เราได้:

- ทบทวน Recursion จาก Part 6 และต่อยอดด้วยแนวคิด **Recursion Tree** เพื่อมองเห็นภาพรวมของ
  การเรียกฟังก์ชันซ้ำๆ
- พิสูจน์ด้วยตัวเลขจริงว่า **Naive Recursive Fibonacci** มีความซับซ้อนแบบ Exponential
  (O(2ⁿ)) และทำไมจึงใช้งานไม่ได้จริงเมื่อ `n` มีค่ามากขึ้น
- เขียน **Memoization (Top-down DP)** เพื่อลดความซับซ้อนของ Fibonacci จาก O(2ⁿ) เหลือ O(n)
  โดยยังคงรูปแบบ Recursive ไว้ แต่เพิ่มการจดจำผลลัพธ์
- เขียน **Tabulation (Bottom-up DP)** ซึ่งแก้ปัญหาเดียวกันด้วย Loop ล้วนๆ ไม่มี Recursion
  และไม่มีความเสี่ยง Stack Overflow
- เข้าใจเงื่อนไข 2 ข้อของปัญหาที่เหมาะกับ DP: **Overlapping Subproblems** และ **Optimal
  Substructure** พร้อมขั้นตอนมาตรฐาน 5 ขั้นในการแก้ปัญหา DP ใดๆ
- แก้ปัญหาคลาสสิก **0/1 Knapsack** และ **Longest Common Subsequence** ด้วย Dynamic
  Programming แบบ Tabulation เต็มรูปแบบ พร้อมเทคนิคย้อนรอย (Backtracking) เพื่อหาคำตอบจริง
  ไม่ใช่แค่ค่าที่ดีที่สุด

Dynamic Programming เป็นหนึ่งในทักษะที่สำคัญที่สุดของโปรแกรมเมอร์ระดับมืออาชีพ และเป็นหัวข้อ
ที่ถูกทดสอบบ่อยที่สุดในการสัมภาษณ์งานสาย Software Engineering (จะฝึกฝนเจาะลึกเพิ่มเติมใน
